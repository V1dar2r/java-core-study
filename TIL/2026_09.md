### ☕ [Java Core] 오늘의 실습 
* **주제:** 람다식(Lambda) 기본 문법
* **개념 요약:** 
  * **람다식이란:** 자바의 메서드를 간결한 함수 식으로 표현한 것이다. 메서드 타입, 반환 값, 메서드 이름, 매개변수 타입, 중괄호, `return`을 생략하고 화살표 기호(`->`)로 코드를 함축하며, 이름이 없어 "익명 함수"라고도 부른다.
  * **람다식과 인터페이스:** 자바에서 익명 함수를 쓰려면 반드시 인터페이스로 타입을 선언해야 하고, 이 인터페이스를 통해 타입을 추론해 람다식이 실행된다. 일반적인 객체 지향 방식은 인터페이스를 `implements`하고 오버라이딩해서 사용하지만, 람다 방식은 추상 메서드가 하나뿐인 인터페이스에 람다식으로 곧바로 구현부를 채워 넣는 방식이다.
  * **함수형 인터페이스:** 추상 메서드가 딱 하나만 선언된 인터페이스를 말한다. `default`, `static`, `private` 메서드는 추상 메서드가 아니므로 여러 개 있어도 상관없고, 추상 메서드가 하나만 있으면 함수형 인터페이스로 인정된다. 람다식은 이 함수형 인터페이스에만 사용할 수 있다. `@FunctionalInterface`를 붙이면 해당 인터페이스에 추상 메서드가 2개 이상 선언됐는지 컴파일러가 확인해준다.
  * **타입 추론 방식:** 람다식의 매개변수 타입을 보고 해당 함수형 인터페이스의 정의를 찾아가 추상 메서드의 형태를 확인한 뒤, 그 타입에 맞춰 람다식의 타입을 자동으로 추론한다.
  * **람다식의 단점:** 
    * 이름이 없는 함수라 별도로 문서화하기 어렵다.
    * 익명 구현 객체 기반이라 디버깅 시 콜 스택 추적이 어렵다.
    * stream 기반 람다식은 일반 for문보다 성능이 떨어진다.
* **💡 배운 점:** 람다식은 자바스크립트에서만 쓰는 개념인 줄 알았는데 자바에도 있다는 걸 새로 알게 됐다. 람다식을 간단히 쓸 때 매개변수 타입이나 반환값을 어떻게 추론하는지 궁금했는데, 함수형 인터페이스를 선언해두면 컴파일러가 그 정의부를 찾아가 타입을 확인하고 추론한다는 원리를 이해했다. 코드가 간결하고 가독성도 좋아 보여 많이 쓰일 것 같지만, 동시에 디버깅과 문서화가 어렵다는 단점도 함께 알게 되었다.

### ☕ [Java Core] 오늘의 실습 
* **주제:** Stream
* **개념 요약:** 
  * **스트림의 3단계:** 스트림은 배열이나 컬렉션의 데이터를 순차적으로 처리하는 기능으로, "생성 → 중간 연산 → 최종 연산" 순으로 진행된다.
    * 생성: 컬렉션이나 배열에서 스트림을 연다.
    * 중간 연산: 데이터를 가공한다. 반환값이 다시 stream이라 연산을 계속 이어 붙일 수 있다.
    * 최종 연산: 실제로 파이프라인을 가동해 결과를 도출하는 단계. 반환 타입이 stream이 아닌 다른 타입이 되면서 스트림이 닫힌다.
  * **stream의 장단점:** for문과 달리 원본 배열을 훼손하지 않고, 코드가 간결해지며 가독성이 좋다. 다만 한 번 사용하면 닫혀버려서 다시 쓰려면 `stream()`을 처음부터 다시 호출해야 한다.
  * **지연 연산(Lazy Evaluation):** 중간 연산은 최종 연산이 호출되기 전까지 실제로 실행되지 않고, 어떤 순서로 실행할지 전략만 구상해둔다. 최종 연산이 호출되는 순간 한 번에 처리되며, 불필요한 데이터는 건너뛰고 필요한 데이터만 순서대로 통과시켜 연산 횟수를 줄여준다.
  * **parallelStream:** 여러 스레드로 데이터를 나눠 병렬로 처리한다. 그만큼 데이터 순서를 보장하지 않고, 데이터 수가 적거나 연산이 단순하면 오히려 성능이 떨어질 수 있다. 스레드 안전성 문제 때문에 공용 변수를 조작하는 작업은 하면 안 되고, 순서를 보장하려면 `forEach` 대신 `forEachOrdered`를 쓸 수 있지만 동기화 비용 때문에 병렬 처리의 이점은 줄어든다.
  * **중간 연산 함수:** 
    * `filter`: 조건에 맞는 데이터만 걸러냄
    * `map`: 데이터를 특정 연산으로 변환
    * `skip`: 앞에서 지정한 개수만큼 건너뜀
    * `limit`: 지정한 개수까지만 사용
    * `boxed`: 원시 타입 → 객체 타입 변환 (반대는 `mapToInt()`)
    * `flatMap`: 중첩된 구조를 평탄화해 1차원 스트림으로 펼침
  * **최종 연산 함수:** 
    * `collect`: 가공된 데이터를 리스트·배열 등 원하는 형태로 변환
    * `forEach`: 각 요소에 반복 작업 수행
    * `count`: 개수를 셈
    * `reduce`: 요소들을 하나의 값으로 합침
    * `anyMatch`: 조건에 맞는 요소가 있는지 검사
    * `findFirst`: 조건에 맞는 첫 요소를 찾는 즉시 나머지는 처리하지 않고 종료해 연산 속도를 줄여줌
* **💡 배운 점:** stream이 단순히 가독성만 좋은 줄 알았는데, for문에서 직접 if문으로 걸러내던 작업을 함수로 빠르게 처리하면서 지연 연산으로 불필요한 연산과 메모리 낭비까지 줄여준다는 걸 알게 되었다. stream이 데이터 가공에 많이 쓰인다는 것도 확인했지만, 너무 많이 남발하면 오히려 디버깅이 어려워지고 가독성이 떨어질 수 있다는 것도 함께 배웠다.

  * **제일 작은 수 제거하기:** 배열을 순회하며 가장 작은 수를 찾고 모든 값을 리스트에 담은 뒤, 마지막에 `remove()`로 그 값을 지우려 했다. 그런데 `remove()`는 값이 아니라 인덱스 번호로 지운다는 걸 에러를 통해 알게 됐고, `indexOf()`로 해당 값의 인덱스를 먼저 찾은 뒤 지우는 방식으로 해결했다.
  * **콜라츠 추측:** 처음엔 오버플로우가 발생해 값이 `-1`로 튀면서 모든 조건을 우연히 피해가고, 횟수만 계속 채워져 500번을 넘기는 방식으로 어쩌다 정답을 맞혔다. 근본 원인은 `int` 범위를 넘는 오버플로우였고, 이를 방지하기 위해 변수를 `long` 타입으로 선언했다. 이후 for문으로 500번을 돌려도 값이 1이 되지 않으면 반복문을 빠져나와 `-1`을 반환하도록 정리했다.
### 🍃 [Spring Boot] 스프링 부트 학습
* **주제:** 빌드 도구(Maven/Gradle), 프로젝트 구조, View 환경설정, 빌드 및 실행
* **핵심 개념 (What & Why):** 
  * **빌드 도구란:** Maven과 Gradle은 필요한 라이브러리를 자동으로 다운받고, 작성한 코드를 실행 가능한 파일로 만들어주는 빌드 도구다. 즉 라이브러리 의존성 관리와 빌드 자동화를 담당한다.
  * **Maven vs Gradle:** 
    * Maven: 설정 파일은 `pom.xml`(XML 언어). 빌드 속도가 느리고 정해진 규칙대로만 사용해야 한다. 비교적 레거시 프로젝트에서 많이 쓰인다.
    * Gradle: 설정 파일은 `build.gradle`(Groovy 또는 Kotlin 언어). Maven보다 빌드 속도가 훨씬 빠르고 빌드 과정을 자유롭게 조작할 수 있어 요즘 프로젝트에서 많이 쓰인다.
  * **의존성(dependency) 개념:** 라이브러리를 선택하면 그 라이브러리 하나만 가져오는 게 아니라, 그 라이브러리가 필요로 하는 다른 라이브러리들까지 Gradle이 함께 가져온다.
  * **Starter 의존성:** 특정 기능에 필요한 관련 라이브러리들을 묶어서 자동으로 포함·설정해주는 패키지. 예를 들어 `spring-boot-starter-web`에는 `spring-boot-starter-tomcat`(내장 톰캣)과 `spring-webmvc`(스프링 웹 MVC)가 들어 있고, `spring-boot-starter-thymeleaf`는 타임리프 템플릿 엔진을 포함한다. 모든 스타터가 공통으로 포함하는 `spring-boot-starter`에는 스프링 부트 코어와 로깅 기능이 들어 있다.
  * **테스트 관련 라이브러리 (`spring-boot-starter-test`):** 
    * JUnit: 테스트 프레임워크
    * Mockito: 가짜 객체(Mock)를 만들어주는 라이브러리
    * AssertJ: 테스트 코드를 더 편하게 작성하도록 도와주는 라이브러리
    * spring-test: 스프링 통합 테스트 지원
  * **프로젝트 생성:** start.spring.io 사이트에서 필요한 설정을 선택해 Spring Boot 프로젝트를 바로 생성할 수 있다.
  * **프로젝트 폴더 구조:** 
    * `.idea`: IDE 설정 파일
    * `gradle`: Gradle 관련 파일
    * `src/main`: 실제 코드
    * `src/main/resources`: 자바 코드를 제외한 모든 파일(설정, 템플릿 등)
    * `src/test`: 테스트 코드
  * **톰캣(Tomcat):** 요청에 따라 자바 코드를 실행하고 데이터베이스를 조회해 동적인 데이터를 만들어내는, 스프링 프로젝트 구동에 필요한 웹 애플리케이션 서버(WAS)다. 스프링 부트를 실행하면 내장 톰캣이 자동으로 함께 실행되므로 웹 서버를 따로 설치할 필요가 없다.
  * **로그를 쓰는 이유:** 로그가 없으면 실행 기록이 남지 않아 에러를 분류하고 추적하기 어렵다. 로그 레벨을 나눠 관리할 수 있고 파일로도 남길 수 있어 관리가 편해진다.
  * **웰컴 페이지(Welcome Page):** `static/index.html` 파일을 만들어두면, 도메인 주소로 접속했을 때 첫 화면으로 자동 노출되는 웰컴 페이지 기능을 사용할 수 있다.
  * **타임리프(Thymeleaf) 동작 방식:** 컨트롤러가 문자열(뷰 이름)을 반환하면, `viewResolver`가 그 이름과 일치하는 HTML 파일을 `src/main/resources/templates` 폴더에서 찾아 화면을 처리한다.
  * **빌드 및 실행 절차:** 
    1. 빌드할 프로젝트 폴더로 이동
    2. `./gradlew build`로 빌드
    3. `cd build/libs`로 빌드된 파일이 있는 폴더로 이동
    4. `java -jar 파일명`으로 실행
  * **GET 방식:** URL을 입력하거나 링크를 클릭해 특정 화면을 요청하는 HTTP 통신 방식이다.
* **💻 오늘의 코드 조각:** 
```java
package hello.hello_spring.Controller;
 
import org.springframework.stereotype.Controller;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.ui.Model;
 
@Controller
public class HelloController {
 
    @GetMapping("hello") // 사용자가 "hello" 경로로 접속하면 이 메서드를 실행하도록 연결
    public String hello(Model model){
        model.addAttribute("data", "dd!!"); // KEY와 VALUE 추가
        return "hello"; // 문자열 반환 → templates 폴더에서 같은 이름의 HTML 파일을 찾아 화면 처리
    }
 
}
```
 
```html
<!DOCTYPE HTML>
<html xmlns:th="http://www.thymeleaf.org"> <!-- 템플릿 엔진 연결 -->
<head>
    <title>Hello</title>
    <meta http-equiv="Content-Type" content="text/html; charset=UTF-8" />
</head>
<body>
<p th:text="'안녕하세요. ' + ${data}">안녕하세요. 손님</p> <!-- 컨트롤러에서 정한 키값을 불러와 출력 -->
</body>
</html>
```
 
### ✨ [Takeaway] 오늘의 깨달음 (공통)
* Spring Boot가 웹사이트(start.spring.io)를 통해 프로젝트와 필요한 라이브러리를 선택해 생성하는 방식이라는 걸 명확히 이해했다.
* 로그를 왜 쓰는지 막연하게만 알고 있었는데, 에러 레벨을 나누고 기록으로 남긴다는 실질적인 이유를 확실히 알게 되었다.
* 웰컴 페이지가 정적 HTML을 불러와 첫 화면으로 보여주는 기능이라는 것도 새로 배웠다.
* Maven과 Gradle의 차이가 유연성·속도·설정 파일명에 있다는 것과, Maven은 레거시 프로젝트에서, Gradle은 현재 많이 쓰인다는 것을 알게 되었다.
* 빌드 도구가 예전엔 직접 해야 했던 작업들을 자동으로 처리해준다는 걸 체감하면서, 왜 의존성 관리를 그렇게 강조하는지 이해가 됐다.
