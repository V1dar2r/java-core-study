### ☕ [Java Core] 오늘의 실습 
* **주제:** 람다식(Lambda) 기본 문법
* **개념 요약:** 
  * **람다식이란:** 자바의 메서드를 간결한 함수 식으로 표현한 것이다. 메서드 타입, 반환 값, 메서드 이름, 매개변수 타입, 중괄호, `return`을 생략하고 화살표 기호(`->`)로 코드를 함축하며, 이름이 없어 "익명 함수"라고도 부른다.
  * **람다식과 인터페이스:** 자바에서 익명 함수를 쓰려면 반드시 인터페이스로 타입을 선언해야 하고, 이 인터페이스를 통해 타입을 추론해 람다식이 실행된다. 일반적인 객체 지향 방식은 인터페이스를 `implements`하고 오버라이딩해서 사용하지만, 람다 방식은 추상 메서드가 하나뿐인 인터페이스에 람다식으로 곧바로 구현부를 채워 넣는 방식이다.
  * **함수형 인터페이스:** 추상 메서드가 딱 하나만 선언된 인터페이스를 말한다. `default`, `static`, `private` 메서드는 추상 메서드가 아니므로 여러 개 있어도 상관없고, 추상 메서드가 하나만 있으면 함수형 인터페이스로 인정된다. 람다식은 이 함수형 인터페이스에만 사용할 수 있다. `@FunctionalInterface`를 붙이면 해당 인터페이스에 추상 메서드가 2개 이상 선언됐는지 컴파일러가 확인해준다.
  * **타입 추론 방식:** 람다식의 매개변수 타입을 보고 해당 함수형 인터페이스의 정의를 찾아가 추상 메서드의 형태를 확인한 뒤, 그 타입에 맞춰 람다식의 타입을 자동으로 추론한다.
  * **람다식의 단점:** 
    * 이름이 없는 함수라 별도로 문서화하기 어렵다.
    * 익명 구현 객체 기반이라 디버깅 시 콜 스택 추적이 어렵다.
    * stream 기반 람다식은 일반 for문보다 성능이 떨어진다.
* **💡 배운 점:** 람다식은 자바스크립트에서만 쓰는 개념인 줄 알았는데 자바에도 있다는 걸 새로 알게 됐다. 람다식을 간단히 쓸 때 매개변수 타입이나 반환값을 어떻게 추론하는지 궁금했는데, 함수형 인터페이스를 선언해두면 컴파일러가 그 정의부를 찾아가 타입을 확인하고 추론한다는 원리를 이해했다. 코드가 간결하고 가독성도 좋아 보여 많이 쓰일 것 같지만, 동시에 디버깅과 문서화가 어렵다는 단점도 함께 알게 되었다.

### ☕ [Java Core] 오늘의 실습 
* **주제:** Stream
* **개념 요약:** 
  * **스트림의 3단계:** 스트림은 배열이나 컬렉션의 데이터를 순차적으로 처리하는 기능으로, "생성 → 중간 연산 → 최종 연산" 순으로 진행된다.
    * 생성: 컬렉션이나 배열에서 스트림을 연다.
    * 중간 연산: 데이터를 가공한다. 반환값이 다시 stream이라 연산을 계속 이어 붙일 수 있다.
    * 최종 연산: 실제로 파이프라인을 가동해 결과를 도출하는 단계. 반환 타입이 stream이 아닌 다른 타입이 되면서 스트림이 닫힌다.
  * **stream의 장단점:** for문과 달리 원본 배열을 훼손하지 않고, 코드가 간결해지며 가독성이 좋다. 다만 한 번 사용하면 닫혀버려서 다시 쓰려면 `stream()`을 처음부터 다시 호출해야 한다.
  * **지연 연산(Lazy Evaluation):** 중간 연산은 최종 연산이 호출되기 전까지 실제로 실행되지 않고, 어떤 순서로 실행할지 전략만 구상해둔다. 최종 연산이 호출되는 순간 한 번에 처리되며, 불필요한 데이터는 건너뛰고 필요한 데이터만 순서대로 통과시켜 연산 횟수를 줄여준다.
  * **parallelStream:** 여러 스레드로 데이터를 나눠 병렬로 처리한다. 그만큼 데이터 순서를 보장하지 않고, 데이터 수가 적거나 연산이 단순하면 오히려 성능이 떨어질 수 있다. 스레드 안전성 문제 때문에 공용 변수를 조작하는 작업은 하면 안 되고, 순서를 보장하려면 `forEach` 대신 `forEachOrdered`를 쓸 수 있지만 동기화 비용 때문에 병렬 처리의 이점은 줄어든다.
  * **중간 연산 함수:** 
    * `filter`: 조건에 맞는 데이터만 걸러냄
    * `map`: 데이터를 특정 연산으로 변환
    * `skip`: 앞에서 지정한 개수만큼 건너뜀
    * `limit`: 지정한 개수까지만 사용
    * `boxed`: 원시 타입 → 객체 타입 변환 (반대는 `mapToInt()`)
    * `flatMap`: 중첩된 구조를 평탄화해 1차원 스트림으로 펼침
  * **최종 연산 함수:** 
    * `collect`: 가공된 데이터를 리스트·배열 등 원하는 형태로 변환
    * `forEach`: 각 요소에 반복 작업 수행
    * `count`: 개수를 셈
    * `reduce`: 요소들을 하나의 값으로 합침
    * `anyMatch`: 조건에 맞는 요소가 있는지 검사
    * `findFirst`: 조건에 맞는 첫 요소를 찾는 즉시 나머지는 처리하지 않고 종료해 연산 속도를 줄여줌
* **💡 배운 점:** stream이 단순히 가독성만 좋은 줄 알았는데, for문에서 직접 if문으로 걸러내던 작업을 함수로 빠르게 처리하면서 지연 연산으로 불필요한 연산과 메모리 낭비까지 줄여준다는 걸 알게 되었다. stream이 데이터 가공에 많이 쓰인다는 것도 확인했지만, 너무 많이 남발하면 오히려 디버깅이 어려워지고 가독성이 떨어질 수 있다는 것도 함께 배웠다.

### 🍃 [Spring Boot] 스프링 부트 학습
* **주제:** 빌드 도구(Maven/Gradle), 프로젝트 구조, View 환경설정, 빌드 및 실행
* **핵심 개념 (What & Why):** 
  * **빌드 도구란:** Maven과 Gradle은 필요한 라이브러리를 자동으로 다운받고, 작성한 코드를 실행 가능한 파일로 만들어주는 빌드 도구다. 즉 라이브러리 의존성 관리와 빌드 자동화를 담당한다.
  * **Maven vs Gradle:** 
    * Maven: 설정 파일은 `pom.xml`(XML 언어). 빌드 속도가 느리고 정해진 규칙대로만 사용해야 한다. 비교적 레거시 프로젝트에서 많이 쓰인다.
    * Gradle: 설정 파일은 `build.gradle`(Groovy 또는 Kotlin 언어). Maven보다 빌드 속도가 훨씬 빠르고 빌드 과정을 자유롭게 조작할 수 있어 요즘 프로젝트에서 많이 쓰인다.
  * **의존성(dependency) 개념:** 라이브러리를 선택하면 그 라이브러리 하나만 가져오는 게 아니라, 그 라이브러리가 필요로 하는 다른 라이브러리들까지 Gradle이 함께 가져온다.
  * **Starter 의존성:** 특정 기능에 필요한 관련 라이브러리들을 묶어서 자동으로 포함·설정해주는 패키지. 예를 들어 `spring-boot-starter-web`에는 `spring-boot-starter-tomcat`(내장 톰캣)과 `spring-webmvc`(스프링 웹 MVC)가 들어 있고, `spring-boot-starter-thymeleaf`는 타임리프 템플릿 엔진을 포함한다. 모든 스타터가 공통으로 포함하는 `spring-boot-starter`에는 스프링 부트 코어와 로깅 기능이 들어 있다.
  * **테스트 관련 라이브러리 (`spring-boot-starter-test`):** 
    * JUnit: 테스트 프레임워크
    * Mockito: 가짜 객체(Mock)를 만들어주는 라이브러리
    * AssertJ: 테스트 코드를 더 편하게 작성하도록 도와주는 라이브러리
    * spring-test: 스프링 통합 테스트 지원
  * **프로젝트 생성:** start.spring.io 사이트에서 필요한 설정을 선택해 Spring Boot 프로젝트를 바로 생성할 수 있다.
  * **프로젝트 폴더 구조:** 
    * `.idea`: IDE 설정 파일
    * `gradle`: Gradle 관련 파일
    * `src/main`: 실제 코드
    * `src/main/resources`: 자바 코드를 제외한 모든 파일(설정, 템플릿 등)
    * `src/test`: 테스트 코드
  * **톰캣(Tomcat):** 요청에 따라 자바 코드를 실행하고 데이터베이스를 조회해 동적인 데이터를 만들어내는, 스프링 프로젝트 구동에 필요한 웹 애플리케이션 서버(WAS)다. 스프링 부트를 실행하면 내장 톰캣이 자동으로 함께 실행되므로 웹 서버를 따로 설치할 필요가 없다.
  * **로그를 쓰는 이유:** 로그가 없으면 실행 기록이 남지 않아 에러를 분류하고 추적하기 어렵다. 로그 레벨을 나눠 관리할 수 있고 파일로도 남길 수 있어 관리가 편해진다.
  * **웰컴 페이지(Welcome Page):** `static/index.html` 파일을 만들어두면, 도메인 주소로 접속했을 때 첫 화면으로 자동 노출되는 웰컴 페이지 기능을 사용할 수 있다.
  * **타임리프(Thymeleaf) 동작 방식:** 컨트롤러가 문자열(뷰 이름)을 반환하면, `viewResolver`가 그 이름과 일치하는 HTML 파일을 `src/main/resources/templates` 폴더에서 찾아 화면을 처리한다.
  * **빌드 및 실행 절차:** 
    1. 빌드할 프로젝트 폴더로 이동
    2. `./gradlew build`로 빌드
    3. `cd build/libs`로 빌드된 파일이 있는 폴더로 이동
    4. `java -jar 파일명`으로 실행
  * **GET 방식:** URL을 입력하거나 링크를 클릭해 특정 화면을 요청하는 HTTP 통신 방식이다.

### 🍃 [Spring Boot] 스프링 부트 학습
* **주제:** MVC, 정적 컨텐츠, API
* **핵심 개념 (What & Why):** 
  * **MVC 패턴:** Model, View, Controller의 약자로, HTML 파일을 프로그래밍해서 동적으로 다루는 방식이다. 각 역할은 다음과 같다.
    * View: 화면을 출력하는 데 집중
    * Controller: 내부 논리(로직) 처리에 집중
    * Model: View에 출력할 데이터를 담는 역할
  * **MVC 동작 흐름:** 웹 브라우저에서 특정 주소로 요청이 들어오면, 내장 톰캣 서버가 컨트롤러에서 해당 주소와 매핑된 함수를 찾는다. 함수를 찾으면 그 함수가 반환한 문자열과 이름이 같은 HTML 파일을 찾아 화면으로 변환해 보여준다. 이때 `@RequestParam`으로 `?key=value` 형태의 URL 파라미터를 함수 인자로 그대로 받아 처리할 수 있다.
  * **정적 컨텐츠(Static Content):** 가공되지 않은 정적 HTML 파일을 그대로 보여주는 방식이다. 요청이 들어오면 먼저 컨트롤러에 매핑된 함수가 있는지 확인하고, 없으면 `resources` 폴더에서 같은 이름의 정적 파일을 찾아 웹 브라우저에 그대로 반환한다.
  * **API 방식:** 데이터를 JSON 형태로 전달하는 방식이다. 템플릿 엔진 방식과 다르게 View(HTML)를 거치지 않고 데이터를 바로 반환한다. 함수가 객체를 반환하면 이를 JSON 형태로 변환해서 응답하며, `@ResponseBody`를 붙이면 반환값이 body에 바로 입력된다.
  * **API 요청 처리 과정:** 웹 브라우저의 요청을 톰캣이 받아 스프링에 넘기면, 스프링이 해당 매핑 함수를 찾아 실행한다. 함수가 객체를 반환하면 `HttpMessageConverter`가 그 객체를 JSON 형식으로 변환해 최종 응답을 만든다.
* **💻 오늘의 코드 조각:** 
```java
@GetMapping("hello-mvc") // mvc(template engine)
public String helloMvc(@RequestParam("name") String name, Model model){
    model.addAttribute("name", name);
    return "hello-template";
}
 
@GetMapping("hello-string")
@ResponseBody // HTML body부에 직접 입력
public String helloString(@RequestParam("name") String name){
    return "hello " + name; // hello spring
} // API와 템플릿 엔진의 차이는 View를 거치지 않고 바로 출력한다는 점
 
@GetMapping("hello-api") // API 방식
@ResponseBody
public Hello helloApi(@RequestParam("name") String name){
    Hello hello = new Hello();
    hello.setName(name);
    return hello;
}
 
static class Hello { 
    private String name;
 
    public String getName(){
        return name;
    }
    public void setName(String name){
        this.name = name;
    }
}
```
 
```html

<body>

</html>
```

    * 도메인: 비즈니스 대상이 되는 객체 자체
  * **테스트 방식:** 기능을 만들고 확인할 때 `main()` 메서드나 컨트롤러로 직접 실행해보는 것보다, JUnit으로 테스트를 작성하는 게 훨씬 편하다.

### 🍃 [Spring Boot] 스프링 부트 학습
* **주제:** 스프링 빈과 의존성 주입
* **핵심 개념 (What & Why):** 
  * **주요 어노테이션:** `@Controller`, `@Service`, `@Repository`, `@Component`, `@Autowired`
  * **웹 요청 처리 흐름:** 
    1. 사용자가 브라우저에서 URL을 입력하거나 버튼을 누르면 HTTP 요청이 발생한다.
    2. 스프링 부트에 내장된 톰캣 서버가 그 요청을 받아 스프링 컨테이너의 `DispatcherServlet`에 전달한다.
    3. `DispatcherServlet`이 요청 내용을 보고 이를 처리할 컨트롤러 스프링 빈을 찾아 호출한다.
    4. 컨트롤러가 호출되면 내부에 `@Autowired`로 연결된 Service, Repository 빈들이 함께 동작하며 로직을 처리한다.
    5. 컨트롤러는 화면에 보여줄 데이터와 화면(파일) 이름을 `DispatcherServlet`에 넘긴다.
    6. `DispatcherServlet`이 `ViewResolver`를 통해 `templates` 폴더에서 해당 화면 파일을 찾고, 톰캣을 거쳐 웹 브라우저로 전송되어 사용자 화면에 출력된다.
  * **브라우저가 보내는 정보:** 요청 방식 + 목적지 주소 + 전달할 데이터 + 메타 정보를 담아 톰캣에 전송한다.
  * **스프링 컨테이너의 역할:** 
    * 프로그램이 시작될 때 스프링 빈들을 생성해 컨테이너에 저장
    * `@Autowired`로 의존 관계가 있는 빈들을 서로 연결
    * 빈 생성 시 초기화 작업을 수행하고, 프로그램 종료 시 빈이 안전하게 소멸되도록 관리
  * **스프링 빈이란:** 개발자가 직접 생성하는 것이 아니라 스프링 부트가 직접 생성하고 관리하는 자바 객체다. 클래스당 하나씩 생성되며(싱글톤), 앱이 실행될 때 자동 생성되고 앱이 종료될 때 함께 소멸된다. 빈들끼리는 `@Autowired`로 자동 연결된다.
  * **빈 등록 방식 1 — 컴포넌트 스캔:** 클래스 위에 어노테이션(`@Controller`, `@Service` 등)을 붙여두면 스프링이 시작 시점에 스캔해서 자동으로 빈으로 등록한다. 단, 스캔 대상 패키지 안에 포함되어 있어야 등록된다.
  * **빈 등록 방식 2 — `@Bean` 수동 등록:** 설정용 클래스(`@Configuration`)를 만들고 그 안의 메서드에서 개발자가 직접 객체를 생성해 반환하면, 스프링이 그 결과물을 빈으로 등록한다. 외부 라이브러리나 수정할 수 없는 내장 클래스를 빈으로 만들 때 주로 사용한다. 참고로 과거에는 XML로 빈을 등록했지만 최근에는 이런 자바 코드 방식이 쓰인다.
  * **의존성 주입 3가지 방법:** 
    * **필드 주입:** 스프링 컨테이너가 없으면 변수에 다른 빈을 연결하기 어렵고, 독립적인 테스트가 힘들다는 단점이 있다.
    * **setter 주입:** 나중에 다른 빈으로 교체할 수 있다는 장점이 있지만, 실행 도중 누군가 setter를 호출해 의도치 않은 빈이 주입될 수 있다는 위험이 있다.
    * **생성자 주입:** `final` 키워드를 써서 프로그램 종료까지 값이 바뀌지 않도록 막을 수 있고, 테스트도 용이하다.
  * **의존성 주입의 원리와 이점:** 업캐스팅과 다형성이 기본 원리이며, 코드를 수정하거나 기능을 변경해도 다른 코드에 영향을 주지 않게 해준다. 나중에 구현 클래스를 교체해야 할 때도 설정 클래스에서 직접 빈으로 등록해두면 코드 한 줄만 수정하면 된다.
  * **주의할 점:** 스프링 빈으로 등록하지 않으면 `@Autowired`가 동작하지 않으며, `new`로 직접 객체를 만들어도 컨테이너와 연결되지 않는다.
* **💻 오늘의 코드 조각:**

### 🍃 [Spring Boot] 스프링 부트 학습
* **주제:** 데이터베이스
* **핵심 개념 (What & Why):** 
  * **타입 매핑:** 자바의 `long` 타입은 SQL에서 `bigint`에 해당한다.
  * **`generated by default as identity`:** 값을 직접 넣지 않으면 DB가 자동으로 값을 채워주는 설정이다.
  * **스프링 부트의 DB 빈 자동 생성:** 스프링 부트가 DB 관련 빈을 자동으로 만들어주기 때문에, 설정 클래스(config)에서 반환하는 DB 구현 클래스만 바꿔주면 DB 접근 방식을 손쉽게 교체할 수 있다. 인터페이스를 통해 구현체를 갈아끼우는 구조이며, 스프링의 의존성 주입 덕분에 기존 코드를 수정하지 않고도 구현 클래스만 변경해 적용할 수 있다.
  * **순수 JDBC의 특징:** 자원 해제가 중요하며, 코드가 길고 예외 처리를 위해 try-catch를 많이 써야 한다는 부담이 있다.
  * **DB 접근 기술의 발전 순서:** 순수 JDBC → JdbcTemplate → JPA → 스프링 데이터 JPA
    * **JdbcTemplate:** JDBC API에서 반복되던 코드를 대부분 제거해주지만, SQL은 여전히 직접 작성해야 한다.
    * **JPA:** 반복 코드 제거뿐 아니라 기본적인 SQL까지 직접 만들어서 실행해준다.
    * **스프링 데이터 JPA:** JPA를 기반으로 한 기술로, 인터페이스만 정의해도 자동으로 구현체를 만들어준다. 기본적인 CRUD는 물론, 특정 데이터를 조회하는 메서드도 이름만 정의하면 자동으로 생성된다.
  * **테스트 관련 어노테이션:** 
    * `@SpringBootTest`: 스프링 컨테이너와 테스트를 함께 실행한다. 순수 자바 코드로만 구성된 테스트보다 시간이 더 오래 걸리며, 이런 이유로 통합 테스트보다 단위 테스트가 더 좋은 테스트로 평가된다.
    * `@Transactional`: 테스트 중 DB에 데이터를 넣더라도 테스트가 끝나면 원래 상태로 롤백되어, 다음 테스트에 영향을 주지 않는다.
  * **참고:** 생성자가 하나뿐이면 `@Autowired`를 생략할 수 있다.

**JPA 리포지토리 (JpaMemberRepository)**
```java
package hello.hello_spring.repository;

import hello.hello_spring.domain.Member;
import jakarta.persistence.EntityManager;

import java.util.List;
import java.util.Optional;

public class JpaMemberRepository implements MemberRepository {
    private EntityManager em;

    public JpaMemberRepository(EntityManager em) {
        this.em = em;
    }

    @Override
    public Member save(Member member) {
        em.persist(member);
        return member;
    }

    @Override
    public Optional<Member> findById(Long id) {
        Member member = em.find(Member.class, id);
        return Optional.ofNullable(member);
    }

    @Override
    public Optional<Member> findByName(String name) {
        List<Member> result = em.createQuery("select m from Member m where m.name = :name", Member.class)
                .setParameter("name", name).getResultList();
        return result.stream().findAny();
    }

    @Override
    public List<Member> findAll() {
        return em.createQuery("select m from Member m", Member.class).getResultList();
    }
}
```

### 💻 [Algorithm] 알고리즘 문제 풀이
* **문제:** 같은 숫자는 싫어, 최대공약수와 최소공배수
* **사용 개념 / 자료구조:** Stack, Math
* **💡 나의 실수 & 해결:** 
  * **같은 숫자는 싫어:** 스택의 값을 배열로 옮기는 과정에서 for문의 조건에 스택의 크기(`stack.size()`)를 사용했는데, `pop()`을 할 때마다 스택 크기가 줄어들어 반복 횟수가 부족해지고 배열 뒷부분에 0만 남는 문제가 발생했다. 조건을 배열의 크기 기준으로 바꿔서 해결했다.
  * **최대공약수와 최소공배수:** 처음에는 두 수 중 큰 수와 작은 수를 찾은 뒤, 최대공약수는 작은 수부터 1까지 내려가며 둘 다 나누어떨어지는 수를 찾고, 최소공배수는 작은 수에 1부터 곱한 값이 큰 수로 나누어떨어지는지 확인하는 방식으로 풀었다. 이후 유클리드 호제법을 재귀 함수로 구현하면 훨씬 간단하다는 걸 알게 되어 그 방식으로 다시 풀었고, 최대공약수를 이용해 최소공배수를 구하는 방법도 함께 적용했다.

### 🍃 [Spring Boot] 스프링 부트 학습
* **주제:** AOP
* **핵심 개념 (What & Why):** 
  * **AOP 이전의 문제:** 모든 메서드의 호출 시간을 측정하려면 메서드 하나하나를 전부 수정해야 한다. 이렇게 되면 유지보수가 어렵고, 그렇다고 공통 로직으로 따로 빼내기도 마땅치 않다. 게다가 시간 측정 로직을 조금이라도 바꾸려면 모든 메서드를 다시 찾아다니며 수정해야 하는 번거로움이 생긴다.
  * **AOP란:** 공통 관심 사항과 핵심 관심 사항을 분리하는 프로그래밍 방식이다. 애플리케이션 전반에 걸쳐 공통으로 사용되는 부가 기능(로깅, 시간 측정 등)을 핵심 비즈니스 로직에서 떼어내는 데 사용된다.
  * **AOP 동작 방식 (프록시):** 메서드 호출 시간 측정을 예로 들면, 스프링 컨테이너에서 호출이 일어날 때 실제 객체가 아닌 프록시(Advice, 일종의 가짜 스프링 빈)가 먼저 호출을 받는다. 프록시가 AOP 코드를 실행하고, `proceed()`가 호출되는 순간 제어권이 실제 대상(target)으로 넘어가 원래 로직이 실행된다.
* **💻 오늘의 코드 조각:** 
```java
package hello.hellospring.aop;

import org.aspectj.lang.ProceedingJoinPoint;
import org.aspectj.lang.annotation.Around;
import org.aspectj.lang.annotation.Aspect;
import org.springframework.stereotype.Component;

@Aspect
@Component
public class TimeTraceAop {

    @Around("execution(* hello.hellospring..*(..))") // 적용할 대상 범위 지정
    public Object execute(ProceedingJoinPoint joinPoint) throws Throwable {
        long start = System.currentTimeMillis();
        System.out.println("Start: " + joinPoint.toString());
        try {
            return joinPoint.proceed(); // 제어권이 실제 target으로 넘어가 원래 로직 실행
        } finally {
            long finish = System.currentTimeMillis();
            long timeMs = finish - start;
            System.out.println("END: " + joinPoint.toString() + " " + timeMs + "ms");
        }
    }

}
```

### ✨ [Takeaway] 오늘의 깨달음 (공통)
* for문의 조건에 값이 계속 변하는 변수를 넣으면 안 되겠다는 걸 체감했다. 함수가 반환하는 정수값이 반복 중에 계속 달라질 수 있다는 점을 미처 생각하지 못했던 것 같다.
* 코드를 로직적으로만 접근할 게 아니라 수학적인 방식으로도 해결할 수 있다는 걸 알게 되어 새로운 관점을 얻은 느낌이다.
* AOP 같은 프로그래밍 기법이 결국 개발자가 비즈니스 로직에만 집중할 수 있게 해주는 방식이라는 걸 명확히 이해했다.

### 🍃 [Spring Boot] 게시판 프로젝트 구현
* **🎯 오늘의 목표 / 구현 기능:** 글 등록 API
* **💡 고민했던 점 & 트러블슈팅:** 
  * **GET 요청은 코드가 아니라 결과물을 가져온다:** 처음엔 GET을 실행했을 때 서버의 코드를 가져오는 건지 출력물을 가져오는 건지 헷갈렸는데, 실행된 결과물을 가져오는 것임을 알게 되었다.
  * **POST API를 주소창에 쳐도 화면이 안 나오는 이유:** 이건 문제가 아니었다. 실제 웹사이트는 자바스크립트가 POST 요청을 보내고 받은 데이터로 화면의 일부만 비동기적으로 재구성하는 방식이라, 주소창에 직접 입력하는 GET 방식과는 동작이 다르다.
  * **기본 생성자가 필요한 이유:** Jackson이 기본 생성자로 객체를 만든 뒤 필드를 자동으로 채워주는데, 파라미터가 있는 생성자를 직접 만들어 채워 넣으면 되지 않나 하는 고민을 했다.
  * **`@RequestBody`에 엔티티가 아닌 DTO를 쓰는 이유:** 실제 엔티티를 쓰면 필요하지 않거나 민감한 정보까지 함께 들어가 보안에 문제가 생긴다. 또한 상황마다 필요한 필드가 달라지기 때문에, 데이터 운반 전용 객체인 DTO로 분리해서 쓴다는 걸 알게 되었다.
* **💻 핵심 코드 조각:** 

**GET 요청 테스트**
```http
GET http://localhost:8080/ping
```
GET은 HTTP 규약상 데이터나 출력물을 조회할 때 사용한다. 위 코드는 해당 주소의 실행 결과물을 조회해 가져오는 요청으로, 출력물뿐 아니라 파일이나 데이터도 가져올 수 있다. 서버가 켜져 있는 상태에서 `.http` 파일을 실행하면 결과를 조회해오고, `.idea/httpRequests` 폴더에 요청 기록과 로그가 저장된다.

**POST 요청 테스트**
```http
POST http://localhost:8080/posts
Content-Type: application/json

{
  "title" : "안녕하세요",
  "content" : "안녕하신지요"
}
```

* **📌 POST 요청 처리 흐름:** 
  1. 톰캣이 요청을 받아 `DispatcherServlet`에 전달한다.
  2. 스프링 컨테이너에서 해당 주소를 `@PostMapping`으로 매핑한 컨트롤러 빈을 찾는다.
  3. `@RequestBody`가 JSON 데이터를 자동으로 객체로 변환한다.
  4. 메서드가 객체를 반환하면, `@RestController`(= `@Controller` + `@ResponseBody`)임을 확인한 스프링이 `HttpMessageConverter`로 객체를 JSON으로 변환한다.
  5. 완성된 JSON이 `.http` 실행창에 표시된다.

* **📌 객체 ↔ JSON 변환 조건:** 
  * 객체를 JSON으로 변환할 때는 getter 메서드가 필요하고, JSON을 객체로 변환할 때는 파라미터가 없는 기본 생성자가 필요하다.
  * 생성자를 직접 만들면 기본 생성자가 사라지므로 따로 추가해야 한다.
  * 다만 `record`를 사용하면 필드만 선언해도 JSON ↔ 객체 변환이 가능하다. `record`는 모든 파라미터를 받는 생성자와 getter를 자동으로 만들어주며, 괄호 안의 데이터는 `private final`로 취급되어 상수처럼 동작한다.

* **📌 엔티티 대신 DTO(`PostCreateRequest`)를 파라미터로 쓴 이유:** 
  * 엔티티를 그대로 쓰면 민감한 정보까지 전부 노출되지만, DTO는 필요하고 안전한 데이터만 담아 보낼 수 있어 보안에 유리하다.
  * 엔티티를 쓰면 Jackson이 요청에 담긴 불필요한 필드까지 채워버려 데이터가 조작될 위험이 있다. 이를 **과다 바인딩(Mass Assignment)** 문제라고 한다.
  * 상황에 따라 필요한 데이터의 모양이 다르다. 제목·내용만 필요할 때도 있고 작성자·조회수만 필요할 때도 있어서, 용도별로 여러 개의 DTO를 만들어 쓸 수 있다.

**컨트롤러 코드**
```java
package project.board.Controller;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RestController;
import project.board.Post.Post;
import project.board.Post.PostCreateRequest;
import project.board.Post.PostRecord;

import java.util.HashMap;
import java.util.Map;

@RestController
public class PostController {
    private final Map<Long, Post> store = new HashMap<>();
    private Long nextId = 1L;

    @PostMapping("/posts")
    public Post create(@RequestBody PostCreateRequest request){ // DTO로 요청 데이터를 받음
        Long id = nextId++;
        Post result = new Post(id, request.getTitle(), request.getContent());
        store.put(id, result);
        return result;
    }

}
```

### ✨ [Takeaway] 오늘의 깨달음 (공통)
* `.http` 파일을 통해 직접 GET, POST 요청을 보낼 수 있다는 걸 알게 되었다.
* 백엔드 로직이 Controller, Service, Repository로 나뉜다는 구조를 이해했다.
* 실제 데이터를 다룰 때 엔티티를 직접 쓰는 게 아니라, DTO라는 전용 객체를 여러 개 만들어 필요한 데이터만 다루는 방식이 왜 필요한지 명확히 이해했다. DTO로 민감한 정보를 제외한 안전한 데이터만 운반함으로써, Jackson이 모든 데이터를 JSON에 담지 못하도록 막을 수 있다는 점도 알게 되었다.

  * **3진법 뒤집기:** 진법 전환 → 손으로 계산할 때와 달리 코드에서는 처음 나온 나머지가 0번 인덱스 → `reverse` → 다시 진법 전환 (`Integer.parseInt(a, n)`으로 n진수를 10진수로 변환 가능)
  * **최소직사각형:** 명함마다 가로·세로 길이 비교 → 큰 값끼리 비교, 작은 값끼리 비교 → 각각의 최댓값으로 답 도출

<details>
<summary>📖 풀이 과정 자세히 보기</summary>

**3진법 뒤집기**  
진법을 변환한 뒤 무조건 `reverse`로 뒤집고 `pow`로 연산해야 한다고 생각했다. 그런데 알고 보니 손으로 계산할 때는 나머지가 아래에서 위로 쌓이는 반면, 코드에서는 위에서 아래로 순서대로 쌓이기 때문에 이미 뒤집힌 상태가 된다는 걸 알게 되어 `reverse` 없이 해결했다.

**최소직사각형**  
명함을 뒤집어서도 넣을 수 있는 상자를 만든다는 목적으로 접근했다. 명함마다 가로와 세로를 비교해 큰 값과 작은 값으로 나눈 뒤, 큰 값은 큰 값끼리 비교해 최댓값을 구하고 작은 값도 작은 값끼리 비교해 최댓값을 구하는 방식으로 해결했다.

</details>

* **🎯 오늘의 목표 / 구현 기능:** 글 목록 조회
* **💡 고민했던 점 & 트러블슈팅:** 
  * **매핑 어노테이션 중복 에러:** `findAll()` 메서드에 `@PostMapping`을 붙였다가 에러가 발생했다. 같은 어노테이션에 같은 주소를 중복으로 지정하면 충돌이 생긴다는 걸 알게 되었고, 조회 요청에 맞게 `@GetMapping`으로 수정해 해결했다.
  * **`@PathVariable`이란:** `@GetMapping` 같은 엔드포인트 매핑에서 URL의 동적인 부분을 중괄호 `{}`로 감싸면, 스프링이 그 경로의 값을 같은 이름의 메서드 매개변수에 자동으로 바인딩해준다.
* **💻 핵심 코드 조각:** 
```java
@GetMapping("/posts")
public List<Post> findAll(){ // 전체 글 목록 조회
    return new ArrayList<>(store.values());
}

@GetMapping("/posts/{id}")
public Post findOne(@PathVariable Long id){ // URL의 {id} 값이 매개변수 id에 자동 바인딩됨
    return store.get(id);
}
```

* `@PathVariable`을 통한 동적 바인딩으로 유동적인 조회가 가능하다는 걸 알게 되었다.
* 프로그램이 처리하는 연산 순서와 사람이 손으로 계산하는 순서가 다를 수 있다는 점을 인지하고 문제를 풀어야겠다는 생각이 들었다.

### 🍃 [Spring Boot] 게시판 프로젝트 구현
* **🎯 오늘의 목표 / 구현 기능:** Entity에 password 필드 추가, Repository 분리 및 DI 적용, DTO(record) 도입, 없는 글 조회 예외 처리
* **💡 고민했던 점 & 트러블슈팅:** 

**1) password 필드 추가**  
Entity에 password 필드를 추가하려면 JSON을 보내는 `.http` 파일만 수정하면 되는 줄 알았는데, Entity(`Post`)와 Controller의 메서드까지 함께 수정해야 한다는 걸 알게 되어 전부 반영했다.

**2) 학습하며 정리한 Q&A**

| 질문 | 답 |
| --- | --- |
| record로 필드만 선언하면 편한가? | 맞다. 단 DTO에만 해당된다. 엔티티(`Post`)는 값이 바뀌어야 하고 JPA가 기본 생성자를 요구해서 record로 만들 수 없다 |
| `Optional<Post>`를 `Optional<PostResponse>`로 못 바꾸나? | 바꿀 수 있다. `Optional`에도 `map`이 있고, 비어 있으면 변환 함수를 아예 호출하지 않는다 |
| 인터페이스 타입만 적으면 어떤 구현체인지 어떻게 아나? | 컨트롤러는 모른다. 스프링이 안다. 서버 시작 시 `@Repository`가 붙은 클래스를 모아두고 `implements` 관계를 보고 주입해준다 |
| 생성자의 인수 이름을 보고 아는 건가? | 아니다. 타입으로 찾는다. 파라미터 이름은 무엇으로 써도 동작하며, 이름을 보는 건 후보가 2개 이상일 때뿐이다 |

**3) 트러블 포인트 — 저장소 설계**
* **저장소가 `PostResponse`를 반환함:** 저장소가 화면 사정까지 알게 된다. 비밀번호를 영영 꺼낼 수 없게 되고, 응답 형태가 바뀔 때마다 저장소를 고쳐야 한다. → 넣는 것과 꺼내는 것은 같은 타입(`Post`)으로 통일.
* **`save()`에서 id가 객체에 안 심김:** id를 Map의 key로만 쓰고 `post` 객체 안에는 넣지 않아서 `getId()`가 계속 null이었다.
* **없는 id 조회 시 터짐:** `store.get()`이 null을 반환해 `.getId()`에서 예외 발생. → `Optional.ofNullable`로 해결.

**4) 트러블 포인트 — 의존성 주입(DI), 네 번 고침**

| 시도 | 문제 |
| --- | --- |
| 1차 | 생성자 파라미터 타입이 구현체였음 |
| 2차 | 파라미터를 받아놓고 `new`로 직접 객체를 만듦 → DI를 쓰는 척만 함 |
| 3차 | `new`는 뺐지만 파라미터 타입이 여전히 구현체 |
| 4차 | 타입은 고쳤지만 필드 이름에 "memory"가 남음 |

* **핵심:** 컨트롤러는 "저장소가 필요하다"까지만 말해야 하고, "메모리 저장소가 필요하다"고 말하면 안 된다. 타입·이름·import 어디에도 저장 방식의 흔적이 남아 있으면 안 된다.

**5) 트러블 포인트 — 없는 글 처리, 세 번 고침**

| 시도 | 결과 |
| --- | --- |
| `orElse(null)` | Optional이 한 일이 0. 그대로 터진다 |
| `orElse(new Post(0L,"","",""))` | 더 나쁨. 200 응답 + 가짜 데이터. 없는 걸 있다고 답하는 셈 |
| `orElseThrow(NPE)` | 방향은 맞음. 단 NPE는 "프로그래머 실수"용이라 진짜 버그와 구분이 안 됨 |

* **💻 핵심 코드 조각:** 

**record 정리**
* `record`는 전체 생성자, 접근자 메서드, `equals()`, `hashCode()`, `toString()`을 자동으로 만들어주고, 모든 필드를 `private final`로 취급해 수정이 불가능하다.
* 접근자 메서드는 `getXxx()`가 아니라 필드 이름 그대로 호출한다.
* 주로 DTO에 사용하며, `static` 메서드로 자기 자신을 반환하는 팩토리 메서드를 만들어두면 여러 DTO를 쓸 때 엔티티만 넘겨서 편하게 변환할 수 있다.

**반환 타입 관련 정리**
* `List`로 반환하면 자동으로 JSON 배열이 된다.
* 반환할 값이 없으면 null이 DTO에 들어가 서버 에러가 발생한다.
* POST로 타입이 맞지 않는 값(예: 숫자 자리에 문자)을 보내면 400 타입 에러가 발생한다.

**DTO (record)**
```java
public record PostCreateRequest(String title, String content, String password){
    public static PostCreateRequest from(Post post){
        return new PostCreateRequest(post.getTitle(), post.getContent(), post.getPassword());
    }
}
```

**Repository**
```java
package project.board.Repository;

import org.springframework.stereotype.Repository;
import project.board.Post.Post;

import java.util.*;

@Repository
public class MemoryPostRepository implements PostRepository {
    private final Map<Long, Post> store = new HashMap<>();
    private Long nextId = 1L;

    @Override
    public Post save(Post post) {
        Long id = nextId++;
        post.setId(id); // Map의 key로만 쓰지 않고 객체에도 id를 심어줌
        store.put(id, post);
        return post;
    }

    @Override
    public Optional<Post> findById(Long id) {
        return Optional.ofNullable(store.get(id)); // 없으면 빈 Optional 반환
    }

    @Override
    public List<Post> findAll() {
        return new ArrayList<>(store.values());
    }
}
```

**Controller**
```java
package project.board.Controller;

import org.springframework.web.bind.annotation.*;
import project.board.Post.Post;
import project.board.Post.PostCreateRequest;
import project.board.Post.PostResponse;
import project.board.Repository.PostRepository;

import java.util.*;

@RestController
public class PostController {
    private final PostRepository postRepository; // 구현체가 아닌 인터페이스 타입으로 주입

    public PostController(PostRepository postRepository){
        this.postRepository = postRepository;
    }

    @PostMapping("/posts")
    public PostResponse create(@RequestBody PostCreateRequest request){
        Post post = new Post(request.title(), request.content(), request.password());
        return PostResponse.from(postRepository.save(post));
    }

    @GetMapping("/posts")
    public List<PostResponse> findAll(){
        return postRepository.findAll().stream().map(PostResponse::from).toList();
    }

    @GetMapping("/posts/{id}")
    public PostResponse findOne(@PathVariable Long id){
        Optional<Post> post = postRepository.findById(id);
        Post result = post.orElseThrow(() -> new NullPointerException("사용자를 찾을 수 없습니다."));
        return PostResponse.from(result);
    }
}
```

### ✨ [Takeaway] 오늘의 깨달음 (공통)
* 문제를 풀 때 기본적인 형변환이나 문자열 함수가 잘 떠오르지 않았다. 앞으로는 풀다가 메서드가 생각나지 않으면 그때그때 정리해두는 방식으로 진행해야겠다.
* 게시판 프로젝트를 하면서 객체 전체를 노출하지 않기 위해 DTO를 쓴다는 걸 체감했다.
* 스프링은 빈을 이름이 아니라 **타입**으로 찾는다.
* `Optional`은 값을 감싸는 게 목적이 아니라, 값이 없을 때 무엇을 할지 강제로 정하게 만드는 것이다. 꺼내자마자 null로 되돌리면 의미가 없다.
* 에러가 나지 않는 게 항상 좋은 건 아니다. 빈 객체를 돌려주면 조용히 거짓말을 하는 셈이다.

### 💻 [Algorithm]
* **문제:** 두 개 뽑아서 더하기, 푸드 파이트 대회
* **개념:** List, String

* **헤맨 지점:** 
  * **푸드 파이트 대회:** 0을 기준으로 반대편을 어떻게 채울지에서 헤맸다.

* **배울 것:** 
  * **두 개 뽑아서 더하기:** 배열 전체 순회 → 안쪽 반복문은 현재 요소의 다음부터 순회 → 더한 값이 이미 있는지 확인 → 없으면 List에 저장
  * **푸드 파이트 대회:** 배열 순회 → 각 음식 개수의 1/2만 문자열에 추가 → 가운데에 0 추가 → `sb.toString() + sb.reverse().substring(1, sb.length())`로 반대편까지 추가

<details>
<summary>📖 풀이 과정 자세히 보기</summary>

**푸드 파이트 대회**

</details>

### 🍃 [Spring Boot] 게시판 프로젝트 구현
* **🎯 오늘의 목표 / 구현 기능:** JPA 연동 및 JpaRepository 구현
* **💡 고민했던 점 & 트러블슈팅:** 

**1) JPA 핵심 개념**
* **`@Id` / `@GeneratedValue`:** `@Id`는 테이블의 기본 키(PK)를 지정하고, `@GeneratedValue`는 그 값을 자동으로 순차 생성하게 한다.
* **`@Entity`와 기본 생성자:** JPA가 내부적으로 객체를 직접 생성하기 때문에, 엔티티 클래스에는 파라미터가 없는 기본 생성자가 반드시 필요하다.
* **JPA란:** 자바에서 관계형 데이터베이스를 다루는 방식을 바꿔주는 ORM 기술의 자바 표준 명세다. 쿼리를 직접 작성하지 않아도 되고, 특정 DB에 종속되지 않는다.
* **스프링 데이터 JPA가 인터페이스만으로 동작하는 이유 (프록시 패턴):** 애플리케이션이 실행되면 스프링 컨테이너가 인터페이스를 발견하고, 그 인터페이스를 구현한 가짜 객체(프록시)를 만든다. 이 프록시 안에 `EntityManager` 호출, 트랜잭션 열고 닫기, 메서드 이름에 맞는 SQL 생성 같은 코드가 들어 있다. 그래서 인터페이스 타입으로 의존성을 주입받기만 하면 스프링이 알아서 맞는 구현체를 넣어준다.

**2) 트러블 포인트 — JpaRepository 구현**
* **① 새 저장소에 `Map`, `nextId`가 따라옴:** 메모리 저장소를 복사해서 시작했기 때문이다. DB를 쓰면 저장 공간은 테이블이, id는 DB가 대신 담당하므로 둘 다 있으면 안 된다.
* **② `flush()`를 구현하라는 에러:** `JpaPostRepository`가 어떤 경로로든 `JpaRepository`를 구현하게 되어버려서, 수십 개의 메서드를 떠안게 된 것이다.

| 관계 | 누가 구현 | 표현 |
| --- | --- | --- |
| `JpaPostRepository` → `PostRepository` | 본인 | `implements` |
| `JpaPostRepository` → DB 일꾼(`JpaRepository`) | 스프링 | 생성자로 받기 |

* **③ 필드 타입에 `JpaRepository`를 꺾쇠 없이 씀:** `<Post, Long>`이 없으면 자바는 무엇을 다루는지 몰라서 `save()`가 `Object`를 돌려준다. import도 없어서 같은 패키지의 비슷한 이름과 섞일 위험이 있었다. → 내가 정의한 인터페이스로 교체.
* **④ `@Repository` 빠짐:** 메모리 저장소 쪽에서 떼어낸 상태라, `PostRepository` 타입의 빈이 0개가 될 뻔했다.
* **⑤ `Unable to determine Dialect`:** 하이버네이트가 DB에 접속해 "너 어떤 DB야?"를 물어보려다 연결에 실패한 것이다. 방언 문제가 아니라 연결 문제였고, 진짜 원인은 아래 H2 연동 트러블슈팅에서 해결했다.

**3) H2 연동 트러블슈팅**  
세 번 막혔고, 세 번 모두 원인은 에러 메시지가 가리킨 곳이 아니었다. 마지막 문제는 아예 에러조차 나지 않았다. 에러 메시지를 그대로 검색했다면 세 번 다 엉뚱한 곳을 파고 있었을 것이다.

| 증상 | 메시지가 가리킨 곳 | 진짜 원인 |
| --- | --- | --- |
| 앱 기동 실패 | `Unable to determine Dialect` | DB 접속 계정 미설정 |
| 앱 기동 실패 (2차) | `Port 8080 was already in use` | IntelliJ에 남아 있던 이전 인스턴스 |
| POST가 저장 안 됨 | 에러 없음 — 그냥 빈 결과 | H2 콘솔이 엉뚱한 빈 DB에 접속됨 |

세 번째는 사실 증상이 아니었다. 저장은 처음부터 정상 동작하고 있었고, 보는 쪽이 틀렸던 것이다.

* **URL 형태가 기본값을 결정한다**  
  `Unable to determine Dialect`는 결과일 뿐이고, 스택트레이스 맨 아래 `Caused by`에 진짜 원인이 있었다.
  ```
  Caused by: HibernateException: Unable to determine Dialect...                     ← 겉으로 보인 에러
  Caused by: JdbcSQLInvalidAuthorizationSpecException: Wrong user name or password  ← 진짜 원인 (맨 아래)
  ```
  Hibernate는 DB에 접속해 메타데이터를 읽어야 방언을 정할 수 있는데, 커넥션이 안 열리니 판단 자체를 못 한 것이다. 여기서 `hibernate.dialect`를 강제로 지정하는 건 증상만 덮는 오답이다.

  계정이 비어 있던 이유는 URL 형태 때문이었다. Spring Boot는 URL을 보고 임베디드 DB인지 외부 DB인지 판단해 기본값을 다르게 준다.

  | URL | username | ddl-auto |
  | --- | --- | --- |
  | `jdbc:h2:mem:...` (임베디드) | `sa` 자동 설정 | `create-drop` |
  | `jdbc:h2:tcp://...` (서버) | 없음 | `none` |

  이 규칙 하나에 두 번 발목을 잡혔다. 계정을 채우자마자 `Table "POST" not found`가 기다리고 있었는데, 이것도 같은 이유(`ddl-auto`가 `none`)였다. 강의나 블로그를 그대로 따라 했는데 안 되면, URL 형태가 글쓴이와 같은지부터 확인해야 한다. `mem`에서 되던 게 `tcp`에선 안 된다.

* **조용한 실패 — 빈 DB를 보고 있었다**  
  "POST가 저장되지 않는다"는 증상은 사실이 아니었다. 저장은 처음부터 잘 되고 있었고, H2 콘솔이 `~/test`가 아닌 `~/.h2.server.properties`라는 빈 DB에 붙어 있었다.

  H2는 존재하지 않는 DB를 지정하면 에러를 내지 않고 조용히 새로 만든다. 오타를 내도 "그런 DB 없음" 같은 경고 없이 텅 빈 DB에 성공적으로 접속된다. 그래서 증상이 에러가 아니라 빈 결과로 나타났고, 이게 진단을 훨씬 어렵게 만들었다. 홈 디렉터리에 DB 파일이 두 개 있다는 게 결정적인 단서였다.

  | 파일 | 내용 |
  | --- | --- |
  | `test.mv.db` | POST, MEMBER 테이블 — 진짜 DB |
  | `.h2.server.properties.mv.db` | 테이블 없음 — 빈 껍데기 |

  에러는 친절한 것이고, 조용한 실패가 가장 비싸다. DB가 비어 보이면 "저장 실패"보다 **"다른 DB를 보고 있음"**을 먼저 의심해야 한다.

* **진단 방법 — 관측 지점 분리하기**  
  POST를 보내고 GET으로 조회하면 둘 다 같은 앱을 거치기 때문에, 저장 문제인지 조회 문제인지 구분할 수 없다. 그래서 앱을 완전히 우회해 별도의 JDBC 연결로 DB를 직접 조회했다.
  ```
  52 | 첫 번째 글 | 첫 번째 내용 | 1111
  54 | 두 번째 글 | 두 번째 내용 | 2222
  ```
  이 두 줄로 "앱은 정상, 보는 쪽이 문제"라고 범위를 절반으로 좁힐 수 있었다. 버그를 쫓을 때는 의심 대상을 거치지 않는 독립적인 관측 경로를 하나 만들어야 한다.

  테스트 도구 자체도 용의선상에 올려야 한다. 중간에 POST가 `400 Bad Request`로 실패했는데, 로그를 보니 `Invalid UTF-8 start byte 0xbf`였다. Windows 셸이 한글을 CP949로 보낸 것이지 앱 버그가 아니었다.

  에러 메시지가 바뀌었다는 건 앞 문제가 해결됐다는 신호다. `Dialect` → `Port 8080`으로 바뀌었을 때 당황하지 말고 다음 단계로 넘어가면 된다.

* **버그가 아니었던 것 — id가 52, 54로 튀는 현상**  
  id가 1, 2, 3이 아니라 52, 54처럼 튀는 건 정상이다. `@GeneratedValue`에 전략을 주지 않으면 `AUTO`가 되고, H2에서는 시퀀스 방식이라 50개씩 미리 당겨서 쓴다.
  ```sql
  create sequence post_seq start with 1 increment by 50
  ```
  매번 DB에 다음 번호를 물어보는 왕복을 줄이기 위한 최적화다. 1, 2, 3으로 만들고 싶다면 `strategy` 속성을 지정하면 된다.

* **참고 — 8080 포트를 잡고 있는 프로세스 확인 (PowerShell)**
  ```powershell
  Get-NetTCPConnection -LocalPort 8080 -State Listen | ForEach-Object { Get-Process -Id $_.OwningProcess }
  ```

* **💻 핵심 코드 조각:**

**스프링 데이터 JPA 인터페이스 (DB 일꾼)**
```java
package project.board.Repository;

import org.springframework.data.jpa.repository.JpaRepository;
import project.board.Post.Post;

public interface JPARepository extends JpaRepository<Post, Long> { // 구현체는 스프링이 프록시로 생성
}
```

**JpaPostRepository (내가 정의한 PostRepository 구현체)**
```java
package project.board.Repository;

import org.springframework.stereotype.Repository;
import project.board.Post.Post;

import java.util.List;
import java.util.Optional;

@Repository
public class JpaPostRepository implements PostRepository {
    private final JPARepository jpaRepository; // Map, nextId 없이 DB 일꾼만 생성자로 주입받음

    public JpaPostRepository(JPARepository jpaRepository){
        this.jpaRepository = jpaRepository;
    }

    @Override
    public Post save(Post post) {
        return jpaRepository.save(post);
    }

    @Override
    public Optional<Post> findById(Long id) {
        return jpaRepository.findById(id);
    }

    @Override
    public List<Post> findAll() {
        return jpaRepository.findAll();
    }
}
```

### ✨ [Takeaway] 오늘의 깨달음 (공통)
* 에러 메시지가 가리키는 곳이 항상 진짜 원인은 아니다. 스택트레이스는 맨 아래 `Caused by`부터 읽어야 한다.
* 에러는 친절한 것이고, 조용한 실패가 가장 비싸다. 결과가 비어 보이면 "저장이 안 됐다"보다 "다른 곳을 보고 있다"를 먼저 의심해야 한다.
* 버그를 쫓을 때는 의심 대상을 거치지 않는 독립적인 관측 경로를 만들어 범위를 좁혀야 한다.
* 스프링 데이터 JPA는 프록시 패턴 덕분에 인터페이스만 정의해도 동작하며, 나는 "내가 구현할 것(`implements`)"과 "스프링에게 받을 것(생성자 주입)"을 구분해야 한다.

### 💻 [Algorithm]
* **문제:** 콜라 문제, 문자열 내 마음대로 정렬하기
* **개념:** 함수형 인터페이스(Comparator), 배열 정렬
* **헤맨 지점**
  * **콜라 문제:** 새로 받은 콜라 개수를 `n`에 반영하지 않았다.
  * **문자열 내 마음대로 정렬하기:** 특정 인덱스의 문자를 기준으로 정렬하는 방법을 떠올리지 못했다.
* **배울 것**
  * **콜라 문제:** `n / a * b`로 새로 받은 콜라 개수를 구한다 → `n = n % a + n / a * b`로 `n`을 갱신한다 → `n < a`가 될 때까지 반복한다.
  * **문자열 내 마음대로 정렬하기:** `Arrays.sort()`에 Comparator(람다)를 넘긴다 → 두 문자열의 `n`번째 문자를 비교한다 → 결과가 양수면 순서를 바꾸고, 0이나 음수면 그대로 둔다 → `n`번째 문자가 같으면 문자열 전체를 사전순으로 비교한다.

<details>
<summary>📝 풀이 회고</summary>

**콜라 문제**
처음에는 새로 받은 콜라를 `n`에 반영하지 않고 `n / a` 값만 더하는 실수를 했다. 반복을 돌아도 `n`이 제대로 줄지 않는 것을 확인하고, 남은 병(`n % a`)과 새로 받은 콜라(`n / a * b`)를 합쳐 `n`을 갱신하도록 고쳐 해결했다.

**문자열 내 마음대로 정렬하기**
처음에는 어떻게 접근해야 할지 감이 오지 않아 힌트를 받아 Comparator로 풀었다. `Character.compare()`나 `compareTo()`의 결과가 양수면 두 원소의 순서를 바꾸고, 아니면 유지하는 방식이다.
다른 풀이로, 각 문자열 앞에 기준 인덱스의 문자를 붙여 리스트에 저장한 뒤 정렬하고, `substring()`으로 앞 글자를 떼어 원래 문자열로 되돌리는 방법도 있어서 직접 시도해 봤다.

</details>

### 🍃 [Spring Boot] 게시판 프로젝트
* **🎯 오늘의 목표:** 저장소 구조를 `PostRepository`(Spring Data JPA) 기반으로 변경

* **💡 트러블슈팅**
  * **문제:** `PostRepository`가 `JpaRepository`를 상속하도록 바꾸자, `PostRepository`를 `implements`하던 `MemoryPostRepository`에서 "`flush()`를 구현하라"는 컴파일 에러가 났다.
  * **원인:** `PostRepository`가 `JpaRepository`를 상속하면서, 이를 구현하는 클래스는 `JpaRepository`의 **모든** 추상 메서드(`flush()` 등)를 직접 구현해야 하게 되었다.
  * **해결:** 인터페이스만 선언해 두면 Spring Data JPA가 실행 시점에 구현체를 자동으로 만들어 준다. 따라서 직접 만든 구현 클래스가 필요 없어 `MemoryPostRepository`와 나머지 기존 Repository 파일을 삭제했다.

* **📚 새로 알게 된 개념: JPA**
  * JPA는 단순히 SQL을 자동으로 만들어 주는 도구가 아니라, **자바 객체와 DB 테이블을 짝지어 주는 기술(ORM)의 표준**이다. SQL 생성은 그 결과로 따라오는 역할이다.
  * `@Entity`를 붙이면 클래스와 테이블이 연결된다.
  * 역할 구분
    * **JPA:** 규칙(명세)
    * **Hibernate:** 그 규칙을 실제로 구현한 라이브러리
    * **Spring Data JPA:** Hibernate 위에서 `JpaRepository`처럼 쉽게 쓰게 해 주는 스프링 도구

* **💻 핵심 코드**
```java
public interface PostRepository extends JpaRepository<Post, Long> {
    // save, findById, findAll 등 기본 메서드는 JpaRepository가 이미 제공한다.
}
```

### ✨ [Takeaway] 오늘의 깨달음
* 정렬 문제에서는 **Comparator(함수형 인터페이스)** 를 먼저 떠올려 보자. 전에 stream으로 풀 때 쓰던 람다도 결국 함수형 인터페이스였다는 것을 알게 되었다.
* 데이터를 **가공하기 쉬운 형태로 바꿨다가 다시 원래 형태로 되돌리는** 접근법도 있다.
* `JpaRepository`를 상속한 인터페이스를 클래스로 `implements`하면 모든 메서드를 직접 구현해야 한다. **인터페이스만 선언하면 구현은 스프링이 해 준다.**
* JPA는 "SQL을 대신 써 주는 도구"가 아니라 "객체와 테이블을 짝지어 주는 기술"이다. 그래서 변경 감지, 연관관계 매핑, 지연 로딩처럼 SQL 생성만으로는 설명되지 않는 기능이 있다.
