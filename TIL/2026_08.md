### ☕ [Java Core] 오늘의 실습 
* **주제:** String의 특징과 메모리 구조
* **개념 요약:** 
  * **메모리 할당:** `String`은 객체이므로 값 자체가 Stack에 쌓이는 것이 아니라, Heap 영역에 생성되고 Stack에는 그 참조값(주소)이 저장된다.
  * **불변성(Immutable):** 자바의 문자열은 불변이다. 값이 변경된 것처럼 보여도, 실제로는 새로운 객체를 생성해 참조값을 바꾸는 것이다.
  * **불변으로 설계된 이유 3가지:** 
    1. 데이터 캐싱(String Constant Pool)을 통한 성능 이득
    2. 참조값이 임의로 변경되지 않아 보안에 유리
    3. 멀티 스레드 환경에서 동기화(Synchronization) 문제가 발생하지 않음 (Thread-safe)
  * **리터럴 vs `new` 연산자:**
    * **리터럴 (`""`):** Heap 영역 내의 `String Constant Pool`에 객체가 생성됨. 같은 문자열이면 기존 참조값을 재사용함 (메모리 절약). `==` 비교 시 `true`.
    * **`new` 연산자:** 호출할 때마다 Heap 영역에 서로 다른 독립적인 객체를 생성함. `==` 비교 시 `false`. (값 비교는 무조건 `.equals()` 사용)
  * **`intern()` 메서드:** 리터럴 방식은 자동으로 `intern()`을 호출하여 Pool에 문자열이 있는지 확인한다. `new`로 만든 객체도 이 함수를 쓰면 Pool을 이용할 수 있다.
* **💡 배운 점:** C++에서는 문자열 값이 변수 자체에 담기고 수정도 가능했지만, Java에서는 '불변 객체의 참조값'을 가진다는 패러다임의 차이를 명확히 이해했다.

### ☕ [Java Core] 오늘의 실습 
* **주제:** `StringBuilder` vs `StringBuffer`
* **개념 요약:** `StringBuilder`와 `StringBuffer`는 모두 가변(Mutable) 문자열 클래스다. `StringBuilder`는 단일 스레드 환경에서 성능이 가장 우수하지만 동기화를 지원하지 않으며, `StringBuffer`는 성능이 조금 낮더라도 멀티 스레드 환경에서 동기화(Thread-safe)를 보장한다. `String` 타입에 `+` 연산자를 사용해 문자열을 이어 붙일 경우, 내부적으로 `StringBuilder` 객체를 생성하여 `append()`를 수행한 뒤 다시 `String`으로 변환해 반환한다. `String`은 불변(Immutable) 객체이므로 수정 작업이 반복되면 Heap 영역에 불필요한 객체가 계속 생성되어 메모리 낭비와 성능 저하를 유발할 수 있다.
* **💡 배운 점:** '그렇다면 `String`은 아예 쓰지 말아야 할까?'라는 의문이 들었지만, `StringBuilder`나 `StringBuffer`는 초기 객체 생성 비용이 들고 내부 버퍼 연산이 필요하다는 것을 알게 되었다. 따라서 변경이 잦지 않은 읽기 전용 문자열에는 여전히 `String`을 사용하는 것이 효율적이다. 또한, 멀티 스레드 환경의 동기화 지원 여부에 따라 두 클래스를 구분해서 사용해야 함을 확실히 이해했다.

### 💻 [Algorithm] 알고리즘 문제 풀이
* **문제:** 배열 만들기 2, 문자열 여러 번 뒤집기, 주사위 게임 3
* **사용 개념 / 자료구조:** `StringBuilder` 클래스, `List` 인터페이스
* **💡 나의 실수 & 해결:** 
  * **배열 만들기 2:** 일반 배열(Array)은 크기가 고정되어 있어 값을 동적으로 추가하기 어렵다. 처음에는 배열 크기를 넉넉하게 선언하려다 인덱스 오류를 겪었고, 크기가 가변적인 `ArrayList`(`List` 인터페이스)를 활용하여 요소를 자유롭게 추가/삭제하며 문제를 해결했다.
  * **문자열 여러 번 뒤집기:** 잦은 문자열 수정 시 `String` 객체가 계속 생성되어 가비지 컬렉터(GC) 부하 및 메모리 문제를 일으킬 수 있다. 이를 방지하기 위해 초기 객체를 한 번만 생성하고, 단일 스레드 환경에서 성능이 뛰어난 `StringBuilder`의 내장 메서드를 활용하여 효율적으로 풀이했다.
  * **주사위 게임 3:** 먼저 주사위 값을 '정렬'한다는 아이디어로 접근했지만, 복잡한 비교 연산(조건문)을 구성하는 데 어려움을 겪었다. 구글링을 통해 조건문이 위에서부터 하나씩 걸러지도록(순차적으로 제외되도록) 분기 처리하는 아이디어를 얻어 코드를 완성할 수 있었다.

### ✨ [Takeaway] 오늘의 깨달음 (공통)
* 무의식적으로 `String` 타입을 남용해 왔는데, 메모리 관점에서 보면 수정이 일어날 때마다 새로운 객체가 무한정 생성된다는 사실을 깊이 체감했다. 앞으로는 상황에 맞게 `StringBuffer`와 `StringBuilder`를 능숙하게 활용해야겠다. 
* 또한, 자바의 기본 배열은 '크기가 고정되어 있다'는 사실을 잊지 않고, 적재적소에 컬렉션 프레임워크(`List` 등)를 적용하는 훈련을 꾸준히 해야겠다고 다짐했다.

## 📅 2026-08-21 (금) TIL

### ☕ [Java Core] 오늘의 실습 
* **주제:** 클래스, 생성자, 메서드 오버로딩
* **개념 요약:** 
  * **클래스, 객체, 인스턴스:** 클래스는 객체의 설계도이며, 객체는 `new` 연산자를 통해 메모리에 할당된 실체다. 인스턴스는 클래스를 바탕으로 구현된 구체적인 객체를 지칭할 때 사용한다.
  * **변수의 종류:**
    * **클래스 변수 (`static`):** 클래스가 로딩될 때 생성되고 프로그램 종료 시 소멸한다. 모든 객체가 값을 공유한다.
    * **인스턴스 변수:** 객체가 생성될 때 만들어지며, 객체마다 고유한 값을 가진다. 객체 소멸 시 함께 사라진다.
    * **지역 변수:** 메서드 블록 내에서 생성되고 블록이 끝나면 소멸한다.
  * **JVM 메모리 구조 변화:** 클래스 메타데이터는 OS가 관리하는 메타스페이스(Metaspace)에 저장되지만, 클래스 변수(static)와 String Constant Pool은 가비지 컬렉터(GC)의 관리를 받기 위해 힙(Heap) 영역에 존재한다.
  * **매개변수 vs 인수:** 매개변수(Parameter)는 메서드를 정의할 때 선언하는 변수이고, 인수(Argument)는 메서드를 호출할 때 실제로 전달하는 값이다.
  * **메서드 오버로딩:** 같은 이름의 메서드를 매개변수의 개수나 타입에 따라 여러 개 정의하는 기능이다. (단, 반환 타입만 다른 경우는 오버로딩이 성립하지 않는다.)
  * **`this` 와 `this()`:** `this`는 인스턴스 자기 자신의 참조 주소를 가리켜 이름이 같은 변수(필드와 매개변수 등)를 구분할 때 쓴다. `this()`는 생성자 내부에서 다른 생성자를 호출할 때 사용한다.
* **💡 배운 점:** `static` 변수가 곧 클래스 변수라는 것을 확실히 인지했다. 또한, static 변수나 문자열 상수 풀이 과거에는 메서드 영역(PermGen)에 있었으나, GC의 효율적인 관리를 위해 힙(Heap) 영역으로 이동했다는 내부 동작 원리를 새롭게 알게 되었다. `this()`가 다른 생성자를 호출하며 오직 생성자 내부에서만 사용 가능하다는 규칙도 명확히 이해했다.

### 💻 [Algorithm] 알고리즘 문제 풀이
* **문제:** QR CODE, 문자열 뒤집기, 접미사 배열
* **사용 개념 / 자료구조:** `StringBuilder` 클래스, `List` 인터페이스
* **💡 나의 실수 & 해결:** 
  * **QR CODE:** 처음에 `String` 타입을 잘라 `StringBuilder`에 추가하려 했으나, 불필요한 String 객체가 연속 생성되어 힙 영역이 낭비될 것을 우려했다. 이에 `char` 형을 이용해 한 글자씩 `append()`로 추가하는 방식으로 최적화했다.
  * **문자열 뒤집기:** 단일 `StringBuilder`로 자르고 뒤집은 뒤 원본을 수정하려 했으나, 단일 문자열 내장 메서드 지원의 한계가 있었다. 이를 해결하기 위해 두 개의 `StringBuilder`를 활용해 범위를 나누어 수정한 뒤, 마지막에 `String`으로 합쳐 반환하는 방식을 사용했다.
  * **접미사 배열:** 자바 내장 메서드의 대소문자 구분(예: `toString()`)을 헷갈려 컴파일 에러를 잡는 데 시간을 허비했다. 또한, `List`를 알파벳 순으로 정렬할 때 `list.sort(null)`처럼 인자에 `null`을 전달해야 기본 오름차순 정렬이 수행된다는 점을 찾아 적용했다.

### ✨ [Takeaway] 오늘의 깨달음 (공통)
* `static` 변수가 단순히 '프로그램 시작부터 끝까지 살아있는 변수'인 것뿐만 아니라 '클래스 변수'로 불린다는 것을 다시금 깨달았다. 특히 이 데이터가 클래스 메타데이터(Metaspace)와 분리되어 힙(Heap) 영역에서 관리되며 가비지 컬렉터의 대상이 될 수 있다는 점을 보며, 자바가 메모리 관리를 위해 얼마나 끊임없이 발전해왔는지 느꼈다.
