### ☕ [Java Core] 오늘의 실습 
* **주제:** String의 특징과 메모리 구조
* **개념 요약:** 
  * **메모리 할당:** `String`은 객체이므로 값 자체가 Stack에 쌓이는 것이 아니라, Heap 영역에 생성되고 Stack에는 그 참조값(주소)이 저장된다.
  * **불변성(Immutable):** 자바의 문자열은 불변이다. 값이 변경된 것처럼 보여도, 실제로는 새로운 객체를 생성해 참조값을 바꾸는 것이다.
  * **불변으로 설계된 이유 3가지:** 
    1. 데이터 캐싱(String Constant Pool)을 통한 성능 이득
    2. 참조값이 임의로 변경되지 않아 보안에 유리
    3. 멀티 스레드 환경에서 동기화(Synchronization) 문제가 발생하지 않음 (Thread-safe)
  * **리터럴 vs `new` 연산자:**
    * **리터럴 (`""`):** Heap 영역 내의 `String Constant Pool`에 객체가 생성됨. 같은 문자열이면 기존 참조값을 재사용함 (메모리 절약). `==` 비교 시 `true`.
    * **`new` 연산자:** 호출할 때마다 Heap 영역에 서로 다른 독립적인 객체를 생성함. `==` 비교 시 `false`. (값 비교는 무조건 `.equals()` 사용)
  * **`intern()` 메서드:** 리터럴 방식은 자동으로 `intern()`을 호출하여 Pool에 문자열이 있는지 확인한다. `new`로 만든 객체도 이 함수를 쓰면 Pool을 이용할 수 있다.
* **💡 배운 점:** C++에서는 문자열 값이 변수 자체에 담기고 수정도 가능했지만, Java에서는 '불변 객체의 참조값'을 가진다는 패러다임의 차이를 명확히 이해했다.

### ☕ [Java Core] 오늘의 실습 
* **주제:** `StringBuilder` vs `StringBuffer`
* **개념 요약:** `StringBuilder`와 `StringBuffer`는 모두 가변(Mutable) 문자열 클래스다. `StringBuilder`는 단일 스레드 환경에서 성능이 가장 우수하지만 동기화를 지원하지 않으며, `StringBuffer`는 성능이 조금 낮더라도 멀티 스레드 환경에서 동기화(Thread-safe)를 보장한다. `String` 타입에 `+` 연산자를 사용해 문자열을 이어 붙일 경우, 내부적으로 `StringBuilder` 객체를 생성하여 `append()`를 수행한 뒤 다시 `String`으로 변환해 반환한다. `String`은 불변(Immutable) 객체이므로 수정 작업이 반복되면 Heap 영역에 불필요한 객체가 계속 생성되어 메모리 낭비와 성능 저하를 유발할 수 있다.
* **💡 배운 점:** '그렇다면 `String`은 아예 쓰지 말아야 할까?'라는 의문이 들었지만, `StringBuilder`나 `StringBuffer`는 초기 객체 생성 비용이 들고 내부 버퍼 연산이 필요하다는 것을 알게 되었다. 따라서 변경이 잦지 않은 읽기 전용 문자열에는 여전히 `String`을 사용하는 것이 효율적이다. 또한, 멀티 스레드 환경의 동기화 지원 여부에 따라 두 클래스를 구분해서 사용해야 함을 확실히 이해했다.

### ☕ [Java Core] 오늘의 실습 
* **주제:** 클래스, 생성자, 메서드 오버로딩
* **개념 요약:** 
  * **클래스, 객체, 인스턴스:** 클래스는 객체의 설계도이며, 객체는 `new` 연산자를 통해 메모리에 할당된 실체다. 인스턴스는 클래스를 바탕으로 구현된 구체적인 객체를 지칭할 때 사용한다.
  * **변수의 종류:**
    * **클래스 변수 (`static`):** 클래스가 로딩될 때 생성되고 프로그램 종료 시 소멸한다. 모든 객체가 값을 공유한다.
    * **인스턴스 변수:** 객체가 생성될 때 만들어지며, 객체마다 고유한 값을 가진다. 객체 소멸 시 함께 사라진다.
    * **지역 변수:** 메서드 블록 내에서 생성되고 블록이 끝나면 소멸한다.
  * **JVM 메모리 구조 변화:** 클래스 메타데이터는 OS가 관리하는 메타스페이스(Metaspace)에 저장되지만, 클래스 변수(static)와 String Constant Pool은 가비지 컬렉터(GC)의 관리를 받기 위해 힙(Heap) 영역에 존재한다.
  * **매개변수 vs 인수:** 매개변수(Parameter)는 메서드를 정의할 때 선언하는 변수이고, 인수(Argument)는 메서드를 호출할 때 실제로 전달하는 값이다.
  * **메서드 오버로딩:** 같은 이름의 메서드를 매개변수의 개수나 타입에 따라 여러 개 정의하는 기능이다. (단, 반환 타입만 다른 경우는 오버로딩이 성립하지 않는다.)
  * **`this` 와 `this()`:** `this`는 인스턴스 자기 자신의 참조 주소를 가리켜 이름이 같은 변수(필드와 매개변수 등)를 구분할 때 쓴다. `this()`는 생성자 내부에서 다른 생성자를 호출할 때 사용한다.
* **💡 배운 점:** `static` 변수가 곧 클래스 변수라는 것을 확실히 인지했다. 또한, static 변수나 문자열 상수 풀이 과거에는 메서드 영역(PermGen)에 있었으나, GC의 효율적인 관리를 위해 힙(Heap) 영역으로 이동했다는 내부 동작 원리를 새롭게 알게 되었다. `this()`가 다른 생성자를 호출하며 오직 생성자 내부에서만 사용 가능하다는 규칙도 명확히 이해했다.

### ☕ [Java Core] 오늘의 실습 
* **주제:** 상속과 다형성 및 업캐스팅
* **개념 요약:** 
  * **상속 (Inheritance):** 기존 클래스(부모/상위)를 재사용해 새로운 클래스(자식/하위)를 작성하는 문법이다. 코드 중복을 줄이고 유지보수와 가독성을 높여준다. 자바는 단일 상속만 지원한다.
  * **생성자와 `super()`:** 자식 클래스의 생성자 첫 줄에는 `super()`(부모 기본 생성자 호출)가 생략되어 있어, 항상 부모 생성자가 먼저 호출된 후 자식 생성자가 실행된다. 부모에 기본 생성자가 없다면 컴파일 에러가 발생하므로 매개변수에 맞춰 명시적으로 `super(...)`를 호출해야 한다.
  * **`this` vs `super`:** 
    * `this`: 자기 클래스 내의 변수 이름이 같을 때 식별하기 위해 사용. `this()`는 자신의 다른 생성자 호출.
    * `super`: 부모 클래스와 자식 클래스의 멤버 변수 이름이 같을 때 식별하기 위해 사용. `super()`는 부모의 생성자 호출.
  * **오버라이딩 vs 오버로딩:** 
    * **오버라이딩(Overriding):** 부모에게 상속받은 메서드의 내부 구현부를 자식 클래스에 맞게 재정의하는 것.
    * **오버로딩(Overloading):** 같은 클래스 내에서 이름이 같은 메서드를 매개변수의 타입이나 개수를 다르게 하여 여러 개 정의하는 것.
  * **패키지와 접근 제어자:** 패키지는 관련 클래스를 모아둔 폴더(도메인)다. `import` 시 `*`를 써도 하위 폴더의 패키지까지 포함되지는 않는다. 
    * 접근 제어자 범위: `public`(제한 없음) > `protected`(같은 패키지 + 타 패키지의 자식) > `default`(같은 패키지) > `private`(같은 클래스 내부)
  * **다형성 (Polymorphism):** 
    * 자료형/매개변수 다형성: 부모 타입의 참조 변수(배열 등)로 다양한 자식 객체를 한 번에 관리하고 입력받아 코드 복잡성을 줄임.
    * 메서드 다형성: 오버로딩과 오버라이딩을 통해 같은 호출로도 다양한 동작을 수행함.
  * **캐스팅 (Casting):**
    * **업캐스팅:** 자식 -> 부모 타입으로 형변환. 자식 고유의 멤버는 사용할 수 없으나, 오버라이딩된 메서드는 자식의 것이 실행된다.
    * **다운캐스팅:** 부모 -> 자식 타입으로 형변환 (업캐스팅된 객체를 되돌릴 때 사용). 괄호를 생략할 수 없으며, 형제 클래스 간 캐스팅은 불가하다.
* **💡 배운 점:** `super()`가 단순히 부모를 가리키는 것을 넘어, 자식 객체를 생성할 때 자동으로 부모 생성자를 먼저 호출하도록 동작한다는 점을 명확히 알게 되었다. 또한 업캐스팅의 목적이 다형성을 활용해 공통된 부분을 간단히 묶어서 처리하기 위함이며, 오버로딩이 단순히 매개변수만 바꾸는 게 아니라 내부 구현부도 상황에 맞게 새로 설계하는 과정임을 깨달았다.

  * **글자 지우기:** 인덱스를 찾음과 동시에 요소를 삭제하면 남은 요소들의 인덱스가 밀려버리는 문제가 발생했다. 이를 해결하기 위해 삭제할 인덱스 위치를 별도의 배열에 미리 표시(마킹)해두고, 문자열을 순회할 때 표시된 위치의 문자는 건너뛰며 `StringBuilder`에 담는 방식으로 해결했다.

### ☕ [Java Core] 오늘의 실습 
* **주제:** 인터페이스와 추상 클래스
* **개념 요약:** 
  * **추상 클래스 (Abstract Class):** 미완성 메서드(추상 메서드)를 하나라도 포함하면 `abstract` 키워드로 선언해야 하는 클래스다. "어떻게 동작하는지"가 아니라 "무엇을 해야 하는지"만 정의하는 설계도 역할을 하며, `new`로 직접 객체를 만들 수 없다.
  * **추상 클래스와 상속:** 자식 클래스는 `super()`로 추상 클래스의 생성자를 호출할 수 있으며, 상속받은 추상 메서드는 반드시 전부 구현해야 한다. 일반 클래스처럼 공통 멤버를 모아 중복을 줄여주지만, 구현을 강제한다는 점과 인스턴스화가 불가능하다는 점에서 일반 클래스와 다르다.
  * **인터페이스 (Interface):** `implements`로 다중 상속이 가능해 여러 기능을 동시에 조합할 수 있고, 인터페이스끼리도 다중 상속이 가능하다. 메서드 앞에는 `public abstract`가 생략되어 있어, 이를 구현하지 않은 클래스는 `abstract`로 표시해야 한다.
  * **인터페이스의 구현 가능한 메서드:** 
    * `private`: 인터페이스 내부에서만 사용
    * `static`: 인터페이스 이름으로 직접 호출
    * `default`: 자식 클래스에서 오버라이딩으로 재정의 가능
  * **인터페이스의 변수:** 선언과 동시에 `public static` 상수가 되어 값을 바꿀 수 없으므로, 추상 클래스처럼 공통 변수를 통합해 관리하는 용도로는 쓸 수 없다.
  * **추상 클래스 vs 인터페이스:** 
    * 추상 클래스: 부모-자식 관계(혈연 관계)의 클래스들을 묶을 때 사용, 기능을 하위 클래스로 확장시키는 개념
    * 인터페이스: 서로 관계없는 클래스들을 연관시킬 때 사용, 정의된 메서드를 각 클래스 목적에 맞게 구현하는 개념
  * **활용 사례:** 추상 클래스를 상속받은 자식 중 특정 추상 메서드가 필요 없는 자식이 있다면, 그 메서드를 인터페이스로 분리해 필요한 자식 클래스에만 상속시키는 방식으로 해결할 수 있다.
* **💡 배운 점:** 인터페이스에는 구현된 메서드가 전혀 없는 줄 알았으나, `private`/`default`/`static` 메서드는 실제 구현이 가능하다는 것을 새로 알게 되었다. 또한 인터페이스의 변수는 `public static` 상수로 취급되어 상속받아도 값을 변경할 수 없다는 점을 확인했다. 추상 메서드는 상속받은 모든 자식이 무조건 구현해야 하는 것과 달리, 인터페이스를 활용하면 해당 기능이 필요한 자식 클래스에만 선택적으로 구현을 강제할 수 있다는 차이를 명확히 이해했다.

### ☕ [Java Core] 오늘의 실습 
* **주제:** ArrayList와 LinkedList 개념 및 성능 비교
* **개념 요약:** 
  * **ArrayList:** 일반 배열과 달리 크기를 가변적으로 늘리거나 줄일 수 있다. 메모리가 연속적으로 저장되지만, 배열처럼 실제 값이 아니라 값이 담긴 주소를 저장한다. 용량이 초과되면 기존 배열을 새 배열에 복사하는 방식으로 늘어나며, 이 과정에서 지연이 발생한다.
  * **ArrayList의 단점:** 중간에 빈 공간을 허용하지 않아 삽입/삭제가 느리고, 배열 크기보다 적게 사용할 경우 메모리 낭비가 생긴다.
  * **LinkedList:** 각 인덱스가 노드로 구성되며, 노드는 자신의 주소·데이터·다음 노드 주소를 가지고 서로 포인터로 연결된다. 메모리가 허용하는 한 무한히 늘어날 수 있고, 앞뒤 노드의 참조 값만 바꾸면 되므로 삽입/삭제가 빠르다. 다만 처음부터 순차적으로 탐색해야 해서 ArrayList보다 탐색 속도가 느리다.
  * **성능 비교 (ArrayList / LinkedList):** 
    * 첫 위치 삽입·삭제: O(N) / O(1) → LinkedList 우세
    * 마지막 위치 삽입·삭제: O(1)·O(N) / O(1) → ArrayList 우세 (LinkedList는 Node 객체를 메모리에 생성하는 작업이 동반되는 반면 ArrayList는 단순히 주소만 저장)
    * 중간 삽입·삭제: O(N) / O(N)+탐색시간+O(1) → LinkedList 우세
    * 탐색: O(N) / O(N) → 연속 저장된 ArrayList가 실질적으로 더 빠름
    * 인덱스로 값 조회: O(1) / O(N) → ArrayList 우세
  * **실제 성능 차이:** 이론상 차이는 있지만 실제로는 나노초 단위라 체감 차이가 거의 없다. LinkedList는 노드가 메모리에 흩어져 있어 Cache Miss가 잦은 반면, ArrayList는 연속 저장이라 Cache Hit이 높다. 또한 삽입/삭제가 느리다는 ArrayList도 OS 레벨의 `System.arraycopy()` 명령어로 나노초 안에 갱신되므로 실질적인 차이는 크지 않다.
* **💡 배운 점:** LinkedList가 주소만 바꾸면 되니 더 유동적이고 성능도 좋을 거라 생각했지만, 실제로는 ArrayList와 차이가 나노초 수준에 불과하고 오히려 잘 쓰이지 않는다는 걸 알게 되었다. 특히 Cache Hit 관점은 생각하지 못했던 부분인데, ArrayList가 연속적으로 저장되기 때문에 Cache Hit이 높다는 사실을 새로 배웠다.
### 💻 [Algorithm] 알고리즘 문제 풀이
* **문제:** 조건에 맞게 수열 변환하기2, 원하는 문자열 찾기, A 강조하기, 특정한 문자를 대문자로 바꾸기
* **사용 개념 / 자료구조:** 배열, 문자열
* **💡 나의 실수 & 해결:** 
  * **조건에 맞게 수열 변환하기2:** `past` 배열을 while문 밖에서 선언한 뒤 `arr`가 바뀔 때마다 `past = arr`로 갱신하려 했으나, 이 방식은 실제 값이 아닌 주소 값을 복사하는 것이라 `arr`가 바뀌면 `past`도 같이 바뀌어버렸다. 이를 해결하기 위해 while문이 반복될 때마다 `Arrays.copyOf()`로 `arr`를 복사해서 `arr`가 변경되기 전 상태를 따로 저장하는 방식으로 해결했다.
  * **원하는 문자열 찾기:** 문자열이 중간에 끊기면 `i = 0`으로만 초기화했는데, 두 문자열이 끝까지 일치하는 경우를 처리하지 못했다. `i = 0`이 될 때 다시 0번째 인덱스와 비교하는 조건문과, for문 종료 후 `i`가 문자열 길이와 같은지 확인하는 조건문을 추가해 해결했다.
  * **A 강조하기:** 소문자 `a`만 조건에 넣었더니 대문자 `A`까지 소문자로 바뀌는 문제가 생겼다. 조건문에 `||`로 대문자 `A`도 함께 넣어 해결했다.
  * **특정한 문자를 대문자로 바꾸기:** 문자열 한 글자를 문자와 어떻게 비교할지 고민했는데, 문자열의 첫 글자는 인덱스 0번째라는 점을 떠올려 `charAt(0)`으로 비교해 해결했다.

### ☕ [Java Core] 오늘의 실습 
* **주제:** HashMap, HashSet
* **개념 요약:** 
  * **HashSet 구조:** 순서가 없고 중복을 허용하지 않는 자료구조다. 저장할 값을 해시 함수에 넣어 나온 결과값을 인덱스로 사용해 저장한다. 내부는 배열과 연결 리스트가 결합된 구조인데, 배열 덕분에 인덱스로 빠르게 접근할 수 있고, 연결 리스트 덕분에 "하나의 인덱스에는 하나의 값만" 저장 가능하다는 배열의 한계를 보완해 한 인덱스에 여러 데이터를 저장할 수 있다.
  * **HashSet의 속도:** 탐색은 key를 해시 함수에 넣어 나온 인덱스에서 연결 리스트를 따라가면 되므로 빠르고, 추가/삭제도 연결 리스트의 참조 값만 바꾸면 되므로 빠르다.
  * **레드-블랙 트리 전환:** 한 인덱스에 노드가 너무 많아지면 연결 리스트 구조가 레드-블랙 트리로 전환된다. 트리는 한 층을 지날 때마다 탐색 범위가 절반씩 줄어 더 빠르지만, 트리 자체가 초기에 저장해야 할 정보가 많아서 처음부터 트리를 쓰지는 않는다.
  * **리사이징:** 배열 용량이 75% 이상 차면 크기를 늘리는 리사이징이 일어나고, 기존에 저장된 값들도 해시 함수에 다시 들어가 재배열된다.
  * **HashMap:** key와 value 쌍으로 저장한다는 점에서 HashSet과 구조가 비슷하다. 사실 HashSet도 내부적으로 key와 value를 쓰는데, key만 해시 함수에 넣어 탐색·저장에 사용하고 value 자리에는 의미 없는 값을 채워 넣는 방식이다. HashMap은 key는 중복될 수 없지만 value는 중복될 수 있다.
  * **HashTable → HashMap:** 예전에는 HashTable 클래스를 썼는데, 멀티 스레드 환경에서 동기화 처리 때문에 한 번에 하나의 프로세스만 접근할 수 있어 느렸고 null도 허용하지 않았다. 이후 등장한 HashMap은 단일 스레드 환경에서 속도를 높이고 null도 허용하게 되었으며, 멀티 스레드 환경에서는 대신 `ConcurrentHashMap`을 사용한다.
  * **체이닝 vs 개방 주소법:** 연결 리스트로 데이터를 연결하는 체이닝 방식은 메모리가 여기저기 흩어져(파편화) Cache Miss가 자주 발생한다는 단점이 있다. 최근 언어들은 데이터 처리가 조금 까다롭더라도 Cache Hit 비율을 높이기 위해 체이닝 대신 개방 주소법을 사용하는 추세다. 이는 캐시 속도의 발전 속도가 메모리 속도의 발전 속도보다 훨씬 빨라져서, 예전에는 버틸 수 있던 캐시 미스의 성능 손해를 지금은 감당하기 어려워졌기 때문이다.
* **💡 배운 점:** HashSet과 HashMap이 완전히 다른 자료구조인 줄 알았는데, 실제로는 HashSet이 HashMap의 일부(key만 쓰는 형태)였다는 걸 알게 되었다. 체이닝 방식이 항상 좋은 줄 알았지만, 데이터 파편화로 Cache Miss가 자주 발생해 성능 면에서는 불리하고 대신 데이터 처리 자체는 유연하다는 장단점을 이해했다. 최근 언어들이 왜 개방 주소법으로 옮겨가는지도 캐시-메모리 속도 차이 관점에서 납득이 됐다.

  * **공백으로 구분하기 1:** 처음엔 for문으로 문자를 순회하다 공백이 나오면 리스트에 저장하는 방식을 계획했는데, `split()` 함수 하나로 문자열을 원하는 기준으로 잘라 배열에 담을 수 있다는 걸 알고 훨씬 간단하게 해결했다.
  * **x 사이의 개수:** `split()`에 인자를 하나만 주면 문자열 끝에 숨겨진 빈 부분은 잘리지 않는다는 걸 알게 되어, 두 번째 인자를 음수로 줘서 끝부분까지 모두 나누도록 했다. 처음엔 삽입/삭제가 쉬운 `List`에 담았다가 `int[]`로 변환했는데, `stream()`의 `mapToInt()`로 길이를 바로 변환해 배열에 담는 방식으로 더 간단히 해결했다.
  * **문자열 잘라서 정렬하기:** 위 문제처럼 `stream()`과 `sort()`로 한 줄에 처리하려다 에러가 났다. `xx`처럼 `x` 사이에 아무것도 없으면 빈 문자열도 배열에 함께 들어가는 게 원인이었다. `filter()`로 빈 문자열을 걸러낸 뒤 정렬해 해결했다.

### ☕ [Java Core] 오늘의 실습 
* **주제:** 제네릭 문법 및 와일드카드
* **개념 요약:** 
  * **제네릭의 캐스팅 제한:** 일반 배열은 객체 타입 간 상하 관계를 이용해 업캐스팅(공변성)이나 다운캐스팅(반공변성)이 가능하지만, 제네릭의 타입 매개변수는 이런 캐스팅이 불가능하다. 그래서 매개변수로 제네릭 타입을 받으면 정확히 그 타입이 아닌 경우 에러가 발생하며, 이를 해결하려면 오버로딩으로 여러 타입의 메서드를 만들거나 고정 타입을 쓰는 방법밖에 없었다. 와일드카드는 이 문제를 해결해준다.
  * **와일드카드 종류:** 
    * `?`: 모든 타입 사용 가능
    * `? extends U`: 상한 경계선. U와 U의 자식 타입까지 사용 가능 (업캐스팅 개념)
    * `? super U`: 하한 경계선. U와 U의 조상 타입까지 사용 가능 (다운캐스팅 개념)
  * **경계 없는 `?`의 문제:** 경계를 정하지 않고 `?`만 쓰면 데이터가 정확히 어떤 타입인지 알 수 없어 읽기/쓰기 모두 에러가 발생한다. 그래서 최소한의 경계를 정하는 `extends`, `super`를 사용한다.
  * **extends와 super의 읽기/쓰기 권한:** 
    * `? extends U` (상한 경계): 읽기는 가능하지만 쓰기는 불가능하다. 배열에 저장하려는 값이 U의 어떤 자식 타입인지 알 수 없기 때문이다. 안전하게 읽으려면 `T` 타입으로 꺼내면 된다.
    * `? super U` (하한 경계): 쓰기는 가능하지만 읽기는 불가능하다. 읽을 때 여러 부모 타입 중 정확히 어떤 타입인지 알 수 없기 때문이다. 대신 `super`는 U 타입과 그 자손 타입만 넣을 수 있어 쓰는 데는 문제가 없다.
  * **사용 기준:** 데이터를 생산(꺼내서 사용)한다면 `? extends T`, 데이터를 소비(값을 넣음)한다면 `? super T`를 사용한다.
  * **`T extends`와 `? extends U`의 차이:** 전자는 제네릭 클래스를 직접 설계할 때 사용하고, 후자는 이미 만들어진 제네릭 클래스를 타입 파라미터로 넘겨받아 메서드의 다형성을 실현할 때 사용한다. `T super` 문법이 없는 이유는, 모든 클래스와 인터페이스가 결국 그 타입이 될 수 있어 `Object`와 다를 게 없어지기 때문이다.
  * **타입 매개변수 이름:** 제네릭 설계 시 쓰는 `T`는 고정된 이름이 아니며, 목적에 맞게 `E`, `K`, `V` 등으로 바꿔 쓰는 것이 관례다.
* **💡 배운 점:** 제네릭 타입에 대해 자세히 몰랐는데 오늘 명확히 이해했다. 제네릭 타입 매개변수는 업캐스팅/다운캐스팅이 불가능하다는 것과, `T` 같은 이름도 고정된 게 아니라 의미에 맞게 바꿔 쓸 수 있는 문자라는 걸 알게 되었다. `extends`와 `super`로 경계를 지정해 데이터의 다형성을 보장한다는 것과, 이 둘이 각각 데이터 소비/생산 역할로 나뉘어 사용된다는 것도 이해했다.

### ☕ [Java Core] 오늘의 실습 
* **주제:** 예외처리
* **개념 요약:** 
  * **오류의 3가지 종류:** 
    * **컴파일 에러:** 컴파일 단계에서 발견되는 문법 오류나 오타. 실행 전에 빨간 줄로 미리 알려주기 때문에 예방이 가능하다.
    * **런타임 에러:** 컴파일은 성공했지만 실행 중에 발생하는 오류. 잘못된 값을 얻거나 프로그램이 비정상 종료된다.
    * **논리적 에러:** 컴파일과 실행 모두 문제없이 되지만 의도한 대로 동작하지 않는 오류. 에러 메시지가 뜨지 않아 코드와 알고리즘을 직접 검토해야 한다.
  * **에러 vs 예외:** 실행 중 발생하는 문제는 에러와 예외로 나뉜다. 에러는 코드로 해결할 수 없는 수준의 오류이고, 예외는 `try-catch`로 프로그램이 종료되지 않게 막을 수 있는 작은 오류다.
  * **예외의 종류와 예시:** 
    * 컴파일 에러(예외): 없는 파일을 참조하거나, 데이터 형식이 잘못되거나, 클래스 이름을 잘못 쓴 경우
    * 런타임 에러(예외): 배열 범위를 벗어나거나, null인 참조 변수의 멤버를 호출하거나, 클래스 간 형 변환이 잘못되거나, 정수를 0으로 나누는 경우
  * **checked / unchecked exception:** 컴파일 에러 계열은 checked exception이라 부르며, `try-catch`로 처리하지 않으면 컴파일 자체가 되지 않는다. 런타임 에러 계열은 unchecked exception으로, 명시적으로 처리하지 않아도 컴파일은 가능하다.
  * **try-catch 동작 방식:** try 블록이 실행되다가 오류가 발생하면 그 즉시 catch 블록으로 넘어가 코드를 실행한다. 오류가 없으면 catch 블록은 실행되지 않는다. catch의 매개변수는 예외 상황에 맞는 예외 클래스를 지정해서 받으며, `Exception` 클래스로 모든 예외를 한 번에 받을 수는 있지만 정확히 어떤 예외인지는 구분할 수 없다.
  * **finally:** try-catch 뒤에 finally 블록을 추가하면, try에서 어떤 일이 일어나든 상관없이 finally는 항상 실행된다.
  * **Exception 클래스의 함수:** 
    * `getMessage()`: 예외 인스턴스에 담긴 메시지를 반환
    * `printStackTrace()`: 예외 발생 당시 호출 스택에 있던 메서드 정보와 예외 메시지를 함께 출력
  * **커스텀 예외:** `Exception` 클래스를 상속받아 나만의 예외 클래스를 직접 만들 수도 있다.
* **💡 배운 점:** 예외 처리 방법 자체는 알고 있었지만, 반드시 처리해야 하는 checked exception과 처리하지 않아도 되는 unchecked exception으로 나뉜다는 건 새로 알게 되었다. 오류를 깊게 구분해본 적이 없었는데, 오늘 런타임 에러·컴파일 에러·논리적 에러 세 가지로 나뉜다는 것을 명확히 배웠다.

  * **뒤에서 5등 위로:** 정렬된 배열을 stream에 올리고 `filter()`로 뒤에서 5등 위 값만 골라내려 했는데, 값에 중복이 있으면 중복된 값까지 함께 걸러져 틀렸다. `skip()` 함수를 찾아 인자로 넘긴 숫자만큼 앞부분을 건너뛰는 방식으로 바꿔 해결했다.
  * **문자열 정수의 합:** `parseInt()`로 한 글자를 정수로 바꾸려 했으나 에러가 발생했다. `parseInt()`는 문자열(String)만 받을 수 있기 때문이었다. 대신 문자 코드에서 `'0'`을 빼는 방식으로 더 간단하게 해결했다.
  * **두 수의 합:** 처음엔 두 문자열의 길이가 다를 수 있다는 생각에 자릿수가 왼쪽부터 시작한다고 착각해서 접근했는데, 실제로는 자릿수가 다를 경우 부족한 왼쪽 자리에 0을 채워야 한다는 걸 깨달았다. 처음에는 길이가 다른 경우를 조건문으로 따로 나눠 처리했지만, 두 문자열을 끝(오른쪽)에서부터 함께 순회하다가 한쪽이 먼저 끝나면 남은 숫자와 올림수만 더하는 방식으로 더 깔끔하게 해결했다.
