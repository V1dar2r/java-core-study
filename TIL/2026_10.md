### 🍃 [Spring Boot] 게시판 프로젝트 구현
* **🎯 오늘의 목표 / 구현 기능:** 글 삭제 API 추가 및 PostNotFoundException 도입
* **💡 고민했던 점 & 트러블슈팅:** 
  처음에는 삭제 API 안에서 내가 만든 조회 API를 호출해 글이 있는지 확인했는데, 이 때문에 글을 삭제할 때 조회수까지 같이 올라가는 문제가 생겼다. 그래서 controller의 조회 함수 대신 JPA가 제공하는 `findById`를 사용하고, `orElseThrow`로 존재하지 않는 id를 삭제하려 할 때 예외를 던지도록 바꿨다.
  예외는 `RuntimeException`을 상속받은 `PostNotFoundException` 클래스를 만들고, 생성자에서 `super`로 에러 메시지를 넘기도록 했다.

  DELETE 요청을 보냈을 때 기본 설정에서는 SQL이 select 1번 + delete 1번으로 총 2번 실행됐다. 그런데 `open-in-view`를 false로 바꾸자 select 2번 + delete 1번으로 총 3번 실행됐다. `deleteById`는 내부에서 한 번 더 `findById`를 호출하는데, open-in-view가 true면 요청이 끝날 때까지 영속성 컨텍스트가 유지되어 두 번째 조회를 1차 캐시에서 가져온다. 반면 false면 `findById`와 `deleteById`가 각각 다른 영속성 컨텍스트에서 실행되어 캐시를 공유하지 못하고 DB에 다시 select를 보낸다.

  영속성 컨텍스트는 엔티티를 영구 저장하고 관리하는 환경으로, 다음과 같은 기능이 있다.
  * **1차 캐시:** 조회한 엔티티를 저장해 두고, 같은 엔티티를 다시 조회하면 DB 대신 캐시에서 가져온다.
  * **쓰기 지연:** 저장할 때마다 insert 쿼리를 바로 보내지 않고, 트랜잭션이 커밋되는 순간 한 번에 DB로 보내 네트워크 비용을 줄인다.
  * **동일성 보장:** 같은 영속성 컨텍스트 안에서 같은 식별자로 조회한 엔티티는 같은 객체임을 보장한다.
  * **변경 감지(Dirty Checking):** 엔티티를 수정할 때 update를 직접 쓰지 않아도, 처음 조회한 상태와 현재 상태를 비교해 자동으로 update 쿼리를 만든다.
  * **지연 로딩(Lazy Loading):** 연관된 객체의 데이터가 실제로 필요한 시점까지 쿼리를 미룬다.

  Spring Boot에서는 `@DeleteMapping` 어노테이션으로 DELETE 요청을 받으며, 해당 경로로 DELETE 메서드 요청이 들어오면 그 메서드가 실행된다.
* **💻 핵심 코드 조각:** (오늘 작성한 코드 중 가장 중요하거나 새롭게 배운 부분)

```java
package project.board.exception;

public class PostNotFoundException extends RuntimeException {
    public PostNotFoundException(Long id) {
        super(id + " id를 찾을 수 없습니다.");
    }
}
```

```java
@DeleteMapping("/posts/{id}")
public PostResponse deleteById(@PathVariable Long id) {
    Optional<Post> post = postRepository.findById(id);
    Post result = post.orElseThrow(() -> new PostNotFoundException(id));
    postRepository.deleteById(id);
    return PostResponse.from(result);
}
```

### ✨ [Takeaway] 오늘의 깨달음 (공통)
* 패턴 문제는 반복되는 패턴을 배열로 선언하고 인덱스 계산으로 풀 수 있다.
* 배열 인덱스는 0부터, 현실의 날짜는 1부터 시작하므로 기준점(baseline)을 맞춰야 한다.
* JPA는 한 번 조회한 엔티티를 1차 캐시에 저장하고, 같은 엔티티를 다시 찾으면 DB에 가지 않고 캐시에서 가져온다.
* 같은 코드라도 `open-in-view` 설정에 따라 실행되는 SQL 수가 달라진다는 것을 로그로 직접 확인했다.

### 💻 [Algorithm]
* **문제:** 소수 찾기, 소수 만들기
* **개념:** 에라토스테네스의 체

* **헤맨 지점:** 소수 만들기에서 내부 for문의 시작 범위를 어떻게 잡을지 헤맸다.
* **배울 것:**
  * **소수 찾기:** boolean 배열 선언 → 2부터 n의 제곱근까지 for문 → 내부 for문으로 i * i부터 n까지 i씩 증가 → i의 배수는 true(소수 아님)로 변경 → 마지막에 false인 값만 개수 세기
  * **소수 만들기:** 3중 for문으로 서로 다른 세 수를 고르는 모든 경우 탐색 → 세 수의 합이 2보다 작으면 false(소수 아님) → 2부터 차례로 나눠서 나누어떨어지면 false, 끝까지 안 나누어떨어지면 true 반환 → true면 result++

<details>
<summary>소수 만들기: 같은 수를 중복으로 고르는 문제</summary>

서로 다른 세 수를 골라야 하는데, 각 for문의 시작점을 0, i, j로 잡았더니 같은 수가 여러 번 뽑히는 문제가 발생했다. 처음에는 if문으로 걸러내려 했지만, 시작점을 `j = i + 1`, `k = j + 1`처럼 1씩 더해서 같은 수를 아예 고르지 않도록 바꿔 해결했다.

</details> 

### 🍃 [Spring Boot] 게시판 프로젝트 구현
* **🎯 오늘의 목표 / 구현 기능:** 게시글 수정 API 구현
* **💡 고민했던 점 & 트러블슈팅:**
  * **PUT vs PATCH:** PUT은 일부만 수정해도 전체 데이터를 다 보내야 해서 불편하다고 판단해 PATCH를 선택했다.
  * **Setter vs 수정 전용 메서드:** setter를 열어두면 어디서든 값을 바꿀 수 있기 때문에, 엔티티 안에 수정 전용 메서드(`update`)를 만드는 방식을 선택했다.
  * **null 처리:** PATCH는 일부 필드만 올 수 있어서 null 처리를 고민했고, 조건문으로 null이 아닌 값만 반영하도록 했다.
  * **엔티티 메서드의 매개변수:** 처음에는 엔티티 메서드가 DTO를 매개변수로 받게 했다. 하지만 이러면 요청 DTO의 필드 이름이 바뀔 때 엔티티까지 수정해야 하는 번거로움이 있어서, 필드 값을 직접 받도록 바꿨다.
  * **@RequestBody 누락:** @RequestBody를 붙이지 않아 스프링이 JSON 본문을 읽지 못하는 문제가 발생했고, 어노테이션을 붙여 해결했다.
* **💻 핵심 코드 조각:**

  @Transactional이 없으면 SELECT만 실행되고 실제 DB는 수정되지 않는다. @Transactional을 붙이면 SELECT 후 UPDATE까지 실행되어 실제 DB가 수정된다. 단, 기존과 같은 값으로 수정하거나 빈 본문을 보내면 바뀐 게 없으므로 SELECT만 실행된다.

```java
public void update(String content, String title) {
    if (content != null) {
        this.content = content;
    }
    if (title != null) {
        this.title = title;
    }
}

@PatchMapping("/posts/{id}")
@Transactional
public PostResponse updateRequest(@PathVariable Long id, @RequestBody PostUpdateRequest postUpdateRequest) {
    Post post = postRepository.findById(id)
            .orElseThrow(() -> new PostNotFoundException(id));
    post.update(postUpdateRequest.content(), postUpdateRequest.title());

    return PostResponse.from(post);
}
```

### ✨ [Takeaway] 오늘의 깨달음 (공통)
* JPA는 트랜잭션이 끝날 때 엔티티에서 달라진 값이 있는지 확인하고(변경 감지, Dirty Checking), 바뀐 부분만 DB에 반영한다는 것을 알게 되었다.
* @Transactional 없이 수정하면 응답에는 바뀐 값이 나오지만 실제 DB는 수정되지 않는다는 것을 알게 되었다.
* @RequestBody가 있어야 JSON 본문을 읽을 수 있다는 것을 다시 깨달았다.
